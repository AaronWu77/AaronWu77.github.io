# Chapter 25 Testing Web Applications

## 25.1 Testing Quality Dimensions

### 25.1.1 Testing Quality Dimensions-I

WebApp 测试首先关注几个基本质量维度：

**Content**

- 在 *syntactic level* 上检查拼写、标点、语法
- 在 *semantic level* 上检查信息正确性、一致性和无歧义性

**Function**

- 检查功能正确性
- 检查稳定性
- 检查是否符合实现标准（如 Java / XML 标准）

**Structure**

- 是否能够正确承载内容与功能
- 是否具备可扩展性
- 当内容或功能增加时，结构是否仍然可支撑

### 25.1.1 Testing Quality Dimensions-II

**Usability**

- 不同类别用户是否都能被界面支持
- 用户是否能学会并正确使用导航语法与语义

**Navigability**

- 是否存在死链、错误链接、不合理跳转
- 所有导航语义和路径是否都得到覆盖

**Performance**

- 系统在不同运行环境、负载和配置下是否仍然响应及时
- 极端负载下是否会出现不可接受的退化

### 25.1.1 Testing Quality Dimensions-III

**Compatibility**

- 在不同客户端与服务端配置下运行 WebApp
- 查找特定主机配置引发的错误

**Interoperability**

- 检查 WebApp 与其他应用、数据库之间的接口协作

**Security**

- 主动评估潜在漏洞并尝试利用它们
- 一旦成功突破，即视为安全失败

---

## 25.2 The Testing Process

WebApp 测试并不是一次性完成的，而是围绕内容、界面、导航、组件、配置、安全与性能逐层展开。

---

## 25.3 Content Testing

### 25.3.1 Content Testing

内容测试有三个主要目标：

1. 找出文本、图形和多媒体中的语法性错误
2. 找出导航过程中呈现内容的语义错误（准确性 / 完整性问题）
3. 找出呈现给用户的内容组织与结构错误

### 25.3.1 Assessing Content Semantics

评估内容语义时，可以从下面几个问题出发：

- 信息是否事实准确？
- 信息是否简洁、直达要点？
- 内容布局是否容易理解？
- 嵌入内容是否容易被找到？
- 是否给出了合适引用？
- 内容在内部以及跨页面之间是否一致？
- 内容是否带有攻击性、误导性或法律风险？
- 是否侵犯版权或商标？
- 内部链接是否正确、是否有补充作用？
- 内容的美学风格是否与界面风格冲突？

### 25.3.2 Database Testing

数据库测试通常按层进行，即：

- 为数据库访问链路中的每一层定义测试
- 检查数据获取、更新、约束与交互是否正确

---

## 25.4 User Interface Testing

### 25.4.1 User Interface Testing

界面测试的关注点包括：

- 界面特性是否符合设计规则与美学要求
- 视觉内容是否能无误地提供给用户
- 单个界面机制是否可按“类单元测试”的方式验证
- 每个界面机制都应放在特定用户类别的 *use-case / NSU* 中测试
- 整体界面需要通过完整用例验证其语义是否合理
- 界面还要在多种浏览器 / 环境下验证兼容性

### 25.4.2 Testing Interface Mechanisms-I

需要重点测试的界面机制包括：

- **navigation mechanisms**：把用户带到其他内容或功能
- **forms**：包含输入字段的结构化文档
- **client-side scripting**：例如 JavaScript 对表单与交互的处理
- **dynamic HTML**：通过脚本或 CSS 在客户端动态操作内容
- **client-side pop-up windows**：自动弹出的内容窗口

### 25.4.2 Testing Interface Mechanisms-II

还包括：

- **CGI scripts**：Web 服务器与用户动态交互的经典方式
- **streaming content**：服务端主动向客户端持续推送内容
- **cookies**：浏览器保存的 WebApp 专用数据块
- **application-specific interface mechanisms**：如购物车、信用卡处理、运费计算器

## 25.5 Usability and Compatibility Tests

### 25.4.3 Usability Tests

可用性测试通常由终端用户执行。

**Testing sequence**

1. 定义可用性测试类别，并为每类设置目标
2. 设计测试以支撑这些目标
3. 选择测试参与者
4. 在测试过程中记录参与者与 WebApp 的交互
5. 建立机制评估可用性结果

可用性可以在不同抽象层级上评估：

- 某个具体界面机制（如一个表单）
- 一整个 Web 页面
- 完整 WebApp

### 25.4.4 Compatibility Testing

兼容性测试的一般做法是：

1. 定义一组常见客户端配置及其变体
2. 构建树状配置结构：
   - computing platform
   - display devices
   - operating systems
   - browsers
   - connection speeds
3. 基于已有界面、导航、性能和安全测试，派生兼容性验证测试

目标是找出那些**由配置差异引起的执行错误**。

---

## 25.6 Component-Level and Navigation Testing

### 25.5 Component-Level Testing

组件级测试关注 WebApp 功能层面的错误发现。

- 可结合传统 *black-box* 与 *white-box* 方法
- 数据库测试往往是其中的重要组成部分

### 25.6 Navigation Testing

导航测试需要覆盖：

- **Navigation links**：站内链接、外部链接、页面锚点
- **Redirects**：错误 URL 或目标页面变化后的重定向
- **Bookmarks**：页面标题是否适合收藏
- **Frames and framesets**：内容、布局、尺寸、下载性能、浏览器兼容性
- **Site maps**：每个条目是否跳转到正确内容
- **Internal search engines**：搜索结果是否准确完整，错误处理是否健全，高级搜索是否有效

---

## 25.7 Configuration Testing

### 25.7.1 Server-side

服务端配置测试要关注：

- WebApp 是否兼容服务器操作系统
- 系统文件、目录和相关数据是否正确创建
- 防火墙、加密等安全措施是否影响执行与性能
- 分布式服务器配置是否经过测试
- 是否能正确集成数据库软件
- 是否对数据库版本敏感
- 服务端脚本是否执行正常
- 管理员误操作是否会影响系统
- 代理服务器配置差异是否经过现场验证

### 25.7.2 Client-side

客户端配置变量通常包括：

- **Hardware**：CPU、内存、存储、打印设备
- **Operating systems**：Linux、Macintosh OS、Windows、移动 OS
- **Browser software**：IE、Mozilla / Netscape、Chrome、Opera、Safari 等
- **UI components**：ActiveX、Java applets 等
- **Plug-ins**：QuickTime、RealPlayer 等
- **Connectivity**：cable、DSL、modem、wifi、3G/4G/5G

由于配置变量过多，实际测试中需要把组合规模缩减到可管理范围。

---

## 25.8 Security Testing

安全测试的范围包括：

- 客户端环境中的漏洞
- 客户端与服务端之间的网络通信
- 服务端环境本身的安全缺陷

**客户端风险**

- 浏览器、邮件程序或通信软件中的既有漏洞

**服务端风险**

- *denial-of-service attacks*
- 恶意脚本
- 借由客户端传播的攻击代码

---

## 25.9 Performance, Load, and Stress Testing

### 25.9.1 Performance Testing

性能测试要回答的问题包括：

- 服务器响应时间是否下降到用户可感知且不可接受的程度？
- 在多少用户数、事务量或数据负载下性能不可接受？
- 性能下降由哪些系统组件引起？
- 各种负载条件下的平均响应时间是多少？
- 性能下降是否影响安全性？
- 随负载增长，WebApp 的可靠性或准确性是否受影响？
- 超过最大容量后会发生什么？

### 25.9.2 Load Testing

负载测试关注 WebApp 及其服务端环境对不同负载条件的响应。

常见变量：

- `N`：并发用户数
- `T`：单位时间在线事务数
- `D`：每个事务处理的数据量

整体吞吐量：

`P = N x T x D`

### 25.9.3 Stress Testing

压力测试要看系统在超出容量时如何失效：

- 系统是逐渐退化，还是直接崩溃？
- 服务器是否提示 *server not available*？
- 用户能否感知系统不可达？
- 请求是否会排队并在压力下降后恢复处理？
- 事务是否会丢失？
- 数据完整性是否受影响？
- 在哪些 `N`、`T`、`D` 下系统会失败？
- 失败的表现形式是什么？
- 是否会自动通知技术支持人员？
- 故障后多久能恢复在线？
- 当容量到达 80% 或 90% 时，是否会主动关闭某些高耗资源功能？

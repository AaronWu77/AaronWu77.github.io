# Chapter 23 Testing Conventional Applications

## 23.1 Testability

一个系统越容易被测试，它的质量风险就越容易暴露。课件中用 *testability* 来描述软件“适合被测试”的程度。

**影响 testability 的因素**

- **Operability**：系统本身运行稳定、干净
- **Observability**：测试结果容易观察
- **Controllability**：测试过程容易控制、自动化和优化
- **Decomposability**：系统可拆分，便于定点测试
- **Simplicity**：结构和逻辑尽量简洁
- **Stability**：测试期间不要频繁改需求
- **Understandability**：设计足够清晰，便于理解

---

## 23.2 What is a Good Test?

**A good test**

- has a high probability of finding an error
- is not redundant
- should be *best of breed*
- should be neither too simple nor too complex

也就是说，一个好的测试用例要么能更容易发现错，要么能覆盖别人覆盖不到的问题，而不是重复堆数量。

---

## 23.3 Internal and External Views

测试传统软件通常有两种视角：

1. **External view / functional view**  
   已知产品应该完成什么功能，据此设计测试，验证功能是否正确。
2. **Internal view / structural view**  
   已知产品内部是如何工作的，据此验证内部操作是否都按规格执行、内部部件是否被充分覆盖。

这两种视角分别对应后续常说的 *black-box testing* 和 *white-box testing*。

---

## 23.4 Test Case Design

测试用例设计的目标是：

- *to uncover errors in a complete manner*
- *with a minimum of effort and time*

但真正的*exhaustive testing* 通常是不可能的。路径数量会随着程序复杂度快速爆炸，因此实际工作中必须采用**选择性测试 (selective testing)**。

> “Bugs lurk in corners and congregate at boundaries.”

这句话也解释了为什么测试尤其要重视边界、分支和不常执行的路径。

---

## 23.5 White-Box Testing

**White-box testing** 的目标是确保所有语句、分支和条件至少被执行一次，从而暴露逻辑错误和错误假设。

课件强调：

- 路径执行概率越低，越容易隐藏逻辑错误
- 人们以为“不可能走到”的路径，往往恰恰会出问题
- 拼写与编码错误具有随机性，未测路径更容易藏 bug

---

## 23.6 Basis Path Testing

*Basis path testing* 的核心思想是：根据程序控制流构造一组**线性独立路径 (linearly independent paths)**，再设计测试用例覆盖这组路径。

**基本步骤**

1. 根据设计或代码画出 *flow graph*
2. 计算其 *cyclomatic complexity*
3. 导出一组 *basis set of linearly independent paths*
4. 设计测试用例，强制执行每条路径

**Cyclomatic Complexity**

圈复杂度可以理解为程序逻辑复杂度的度量：

- 与控制流图中的区域数相关
- 常见表达为 `V(G) = E - N + 2` 或 `P + 1` 的等价形式
- `V(G)` 越高，模块越容易出错

**Basis Path Testing Notes**

- 不一定非要完整流程图，但画图有助于跟踪路径
- 每个简单逻辑测试都要计入复杂度
- 复合条件要按多个判定来考虑
- 这类方法尤其适合*critical modules*

---

## 23.7 Graph Matrices

*Graph matrix* 是与 *flow graph* 对应的方阵：

- 行和列都对应控制流图中的节点
- 矩阵项表示节点之间是否存在边
- 若为边附加权重，还可以进一步分析控制结构

它可以作为测试时分析程序控制流的一种辅助工具。

---

## 23.8 Control Structure Testing

### Condition Testing

*condition testing*：针对程序模块中的逻辑条件设计测试，关注条件表达式是否正确。

### Data Flow Testing

*data flow testing*：按照变量的定义与使用位置选择测试路径。

核心关注：

- `DEF(S)`：语句 `S` 中定义了哪些变量
- `USE(S)`：语句 `S` 中使用了哪些变量
- *definition-use chain (DU chain)*：从变量定义到使用之间的活跃链路

这类方法很适合发现变量未初始化、错误覆盖、错误使用等问题。

### Loop Testing

循环测试主要针对三类情况：

- *simple loops*
- *nested loops*
- *concatenated loops*

**Simple loop** 常见测试点：

1. 完全跳过循环
2. 仅执行一次
3. 执行两次
4. 执行 `m` 次，其中 `m < n`
5. 执行 `n-1`、`n`、`n+1` 次，其中 `n` 为允许的最大循环次数

**Nested loops**

- 从最内层循环开始测
- 外层循环先固定在最小值
- 逐层向外扩展测试

**Concatenated loops**

- 若循环彼此独立，可分别按 simple loop 测
- 若彼此相关，则按 nested loop 处理

## 23.9 Black-Box Testing

黑盒测试关注“输入输出行为”，而不是内部实现。

它通常回答下面这些问题：

- 如何测试功能有效性？
- 如何测试系统行为和性能？
- 哪些输入类别适合做测试用例？
- 系统是否对某些输入特别敏感？
- 如何隔离数据类的边界？
- 系统能承受多大的数据速率和数据量？
- 某些数据组合会对系统运行造成什么影响？

---

## 23.10 Graph-Based Methods

*Graph-based methods* 用图来表示软件对象及其关系。

这里的“对象”并不只指面向对象中的对象，也包括：

- data objects
- modules / components
- object-oriented elements

通过图结构可以分析对象关系、状态转换和交互路径，从而辅助设计测试。

---

## 23.11 Equivalence Partitioning

*Equivalence class* 表示一组在测试意义上等价的输入状态。

核心思想是：如果某一类输入都应表现相同，就没必要把这类输入全都测一遍，只需选代表值。

**Guidelines**

- 输入是区间：定义 1 个有效类和 2 个无效类
- 输入要求特定值：定义 1 个有效类和 2 个无效类
- 输入是集合成员：定义 1 个有效类和 1 个无效类
- 输入是布尔值：定义 1 个有效类和 1 个无效类

---

## 23.12 Boundary Value Analysis

*Boundary value analysis* 专门针对边界值设计测试，因为错误最容易出现在边界附近。

**Guidelines**

- 若输入范围为 `a` 到 `b`，要测试 `a`、`b`、略小于 `a`、略大于 `a`、略小于 `b`、略大于 `b`
- 若输入要求特定数量，也要测试最小值、最大值以及略大略小值
- 输出条件同样要测边界
- 若内部数据结构本身有边界（例如数组大小限制），也必须专门测试

---

## 23.13 Other Black-Box Techniques

### Comparison Testing

- 常用于对可靠性要求极高的软件
- 多个独立团队依据同一规格说明分别实现系统
- 使用相同测试数据验证输出是否一致
- 运行时并行比较结果，发现偏差

### Orthogonal Array Testing

- 适用于输入参数较少、且每个参数取值范围清晰时
- 用较少测试组合覆盖更多参数交互关系

### Model-Based Testing

1. 分析或建立软件的 *behavioral model*
2. 找出能触发状态转换的输入
3. 标注每次状态转换时的预期输出
4. 执行测试
5. 比较实际结果与预期结果

---

## 23.14 Software Testing Patterns

测试模式与设计模式类似，也可以按模式化方式进行描述。

例如 *ScenarioTesting*：

- 在完成单元测试和集成测试之后
- 仍然需要从用户视角验证软件是否满足真实使用需求
- 若这一层失败，说明软件没有满足用户可见需求

因此，测试并不只是一组零散技巧，也可以沉淀为可复用的*patterns*。

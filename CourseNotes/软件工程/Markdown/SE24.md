# Chapter 24 Testing Object-Oriented Applications

## 24.1 OO Testing

为了充分测试面向对象系统，课件强调必须完成三件事：

1. 扩展测试定义，把错误发现技术应用到 OO 的分析与设计模型
2. 显著调整单元测试与集成测试策略
3. 在测试用例设计时考虑 OO 软件的独特特征

也就是说，OO 测试不只是“把传统测试搬过来”，而是要适配类、对象、消息、继承和协作关系。

---

## 24.2 Testing OO Models

审查 OO 分析与设计模型非常重要，因为相同的语义构造——例如：

- *classes*
- *attributes*
- *operations*
- *messages*

会同时出现在分析、设计和代码层。

因此，如果在分析阶段就发现类属性定义有问题，就能避免问题一路传播到设计或编码阶段，减少后续副作用。

---

## 24.3 Correctness of OO Models

在分析与设计阶段，可以通过模型是否符合真实问题域来判断其*semantic correctness*。

如果一个模型在当前开发阶段所需的抽象层级上，能够准确反映真实世界，那么它在语义上就是正确的。

**常见检查点**

- 将模型交给领域专家评审
- 检查类定义和类层次是否存在遗漏与歧义
- 检查类之间的关系是否准确反映现实对象关系

---

## 24.4 Class Model Consistency

类模型一致性检查可以从 *CRC model* 和 *object-relationship model* 出发。

**检查步骤**

1. 回看每张 CRC 卡片
2. 判断被委托的职责是否真的属于 collaborator 的定义范围
3. 反向检查连接关系，确认请求是否来自合理来源
4. 判断是否缺少某些类，或职责是否被错误分组
5. 判断多个频繁请求的职责是否应该合并

这一部分的重点是：**职责划分是否合理，类协作是否自然。**

---

## 24.5 OO Testing Strategies

### Unit Testing

在 OO 中，*unit* 的含义已经改变：

- 最小可测试单元不再是一个独立函数或过程
- 而是封装后的 *class*
- 单个操作通常不能脱离类上下文被孤立测试

### Integration Testing

常见 OO 集成测试策略包括：

- **Thread-based testing**：围绕某个输入事件，把完成该响应所需的一组类集成起来测试
- **Use-based testing**：先测试几乎不依赖服务类的 *independent classes*，再逐层测试依赖类
- **Cluster testing**：把协作紧密的一组类作为一个 *cluster*，设计测试用例暴露协作错误

### Validation Testing

- 当测试进入验证阶段时，类之间的细节连接逐渐退居幕后
- 可以回到需求模型中的 *use cases*
- 结合传统 *black-box testing* 方法驱动验证测试

---

## 24.6 Testing Methods

### Fault-Based Testing

*Fault-based testing* 的思路是：

- 先推测实现中哪些地方最可能出错
- 再设计测试去专门触发这些潜在缺陷

它强调“有针对性地找 plausible faults”。

### Class Testing and the Class Hierarchy

继承不会减少测试工作，反而可能使测试更复杂。

- 所有派生类仍然需要充分测试
- 因为继承层次会带来状态共享、重写行为和多态影响

### Scenario-Based Test Design

*Scenario-based testing* 更关注用户做什么，而不是产品内部怎么实现。

它通常通过 *use-cases* 捕获用户任务，再把这些任务及其变体转化为测试。

---

## 24.7 OOT Methods: Random Testing

*Random testing* 在 OO 场景下通常包括：

1. 找出某个类可用的操作
2. 明确这些操作的使用约束
3. 定义一个最小测试序列
4. 生成多组随机但有效的操作序列
5. 让对象经历更复杂的“生命周期”

这里的重点是通过不同操作序列，观察对象在各种状态变化中的表现。

---

## 24.8 OOT Methods: Partition Testing

*Partition testing* 的目标是减少类测试所需的测试用例数量，其思想类似传统软件中的*equivalence partitioning*。

常见划分方式包括：

- **state-based partitioning**：按操作是否会改变类状态来分类
- **attribute-based partitioning**：按操作使用了哪些属性来分类
- **category-based partitioning**：按操作执行的通用功能来分类

---

## 24.9 OOT Methods: Inter-Class Testing

多类测试 (*multi-class testing*) 关注对象之间的消息传递链路。

基本思路是：

1. 以某个 client class 为起点
2. 根据类操作生成测试序列
3. 追踪这些操作向 server classes 发送的消息
4. 再追踪 server 对象进一步触发的消息
5. 持续向下展开，形成跨类协作测试序列

因此，OO 测试不仅测单个类，还要测**类与类之间的合作过程**。

---

## 24.10 OOT Methods: Behavior Testing

行为测试 (*behavior testing*) 的目标是获得充分的*state coverage*。

也就是说，设计出的操作序列应该能够让类实例穿过所有允许状态。例如：

- 对某个 `Account` 类
- 测试用例应尽量驱动它经历所有合法状态转换

这种方法本质上是把状态图思想引入 OO 测试。

---

## 24.11 Summary

面向对象测试与传统测试相比，差异主要体现在：

- 测试对象从函数 / 模块转向类 / 对象
- 测试重点从局部逻辑扩展到消息与协作
- 模型评审在早期阶段尤其重要
- 继承、多态和状态变化都会增加测试复杂度

所以 OO 测试的核心不只是“测代码”，更是**测模型、测协作、测状态、测场景**。

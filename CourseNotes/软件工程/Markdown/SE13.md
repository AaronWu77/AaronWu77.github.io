# Chapter 13 Architectural Design

## Why Architecture?
架构不是运行中的软件本身，而是帮助我们理解系统结构的设计表示。

- 用来分析设计是否满足需求
- 用来比较架构备选方案
- 用来降低构建风险

## Why Architecture Is Important
架构是需求、设计、实现之间的桥梁。

- 便于 stakeholder communication
- 影响后续所有设计决策
- 帮助团队尽早发现结构性问题

## Architectural Descriptions
一个架构通常需要多个视图来描述。

- architectural description（AD）是架构文档集合
- 不同 view 对应不同 stakeholder concerns
- 重点是“谁关心什么，就看什么视角”

## Architectural Genres and Styles
Genre 体现应用领域的大类，style 则描述具体结构模式。

- data-centered architecture
- data flow architecture
- call and return architecture
- object-oriented architecture
- layered architecture
- service-oriented architecture

## Architectural Patterns
架构模式处理更大的结构性问题。

- concurrency
- persistence
- distribution
- broker 负责分布式组件之间的中介通信

## Architectural Design Steps
架构设计要先放到系统上下文里看。

- 确定外部实体
- 识别 archetypes
- 细化 component structure
- 明确接口和交互方式

## Architectural Considerations
一个好的架构要兼顾多个质量属性。

- economy：少而精
- visibility：结构和决策容易看懂
- spacing：关注点分离
- symmetry：结构均衡一致
- emergence：允许系统出现自组织行为

## Architectural Tradeoff Analysis
架构评估不是看单一指标，而是看质量属性之间的取舍。

- 收集场景和约束
- 选择候选 styles/patterns
- 分析质量属性敏感性
- 找出 tradeoff

## Architectural Complexity and ADL
复杂性会来自组件之间的依赖关系。

- sharing dependencies
- flow dependencies
- constrained dependencies
- ADL 用来描述架构的语法和语义

## Architecture Reviews
架构评审要尽早发现结构层面的风险。

- 检查是否满足质量需求
- 用原型、场景和 checklist 做评审
- 尽量在编码前修正问题

## Pattern-Based Architecture Review
模式化架构评审关注“结构是否和模式一致”。

- 对照 use case 看质量属性
- 检查模式与结构的匹配度
- 记录问题并修正 walking skeleton

## Agility and Architecture
敏捷不是不要架构，而是要用能演化的架构。

- 用 walking skeleton 先搭骨架
- 每个 sprint 都可演进
- 架构评审可直接针对增量代码进行

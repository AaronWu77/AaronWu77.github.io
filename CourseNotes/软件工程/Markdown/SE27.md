# Chapter 27 Security Engineering

## Why Security Engineering?

Security 不能只靠事后修 bug，而必须在设计阶段就纳入系统目标。

- assets 包括信息、文件、程序、存储、处理能力等
- security 关注资产是否被保护
- 只靠漏洞报告补救，通常太晚

---

## 27.1 Analyzing Security Requirements

security requirements 分析的核心是 threat analysis。

1. 识别可能损害系统资源的 threats
2. 设计 controls
3. 用 controls 预防攻击并减轻损害

---

## 27.2 Online Security Threats

在线环境里，很多新平台会放大安全问题。

- **Social Media**：第三方应用可能接触用户隐私
- **Cloud Computing**：带来更多 confidentiality 和 trust 问题
- **Internet of Things**：设备会持续暴露用户上下文信息

---

## 27.3 Security Engineering Analysis

安全工程分析通常要结合用户威胁建模与风险分析。

- 定义 security policies
- 明确外部接口要求
- 描述软件安全要求和运行规则
- 用 state model 检查允许的状态转换
- 用 formal security models 提高系统可信度
- 将 review / inspection / test 的结果汇总成 security case

---

## 27.4 Security Assurance

security assurance 关注的是：我们有哪些证据能证明系统足够安全。

- reviews
- proofs
- test evidence
- audit evidence

这些证据要能支撑对外的安全论证。

---

## 27.5 Security Risk Analysis

风险分析的任务是给 threats 评估优先级。

- 识别威胁
- 评估可能性和影响
- 决定优先防护对象
- 把资源用在最关键的风险上

---

## 27.7 System Trustworthiness

trustworthiness 不是主观印象，而是可验证的系统属性。

- verification 要有可量化、可追溯的依据
- trust metrics 通常依赖历史数据
- 目标是让用户和利益相关者对系统形成可信判断

## 一、什么是流水线？

### 1.1 定义

> **流水线（Pipelining）**：一种使 CPU 更快的实现技术，通过**在同一时刻让多条指令的不同执行阶段重叠**来提高吞吐量。

核心思想：**不等上一条指令完全完成，就开始执行下一条指令的某个阶段**——就像洗衣服流水线一样。

### 1.2 洗衣机类比（理解流水线的直觉）

假设 Ann、Brian、Cathy、Dave 各有一筐衣服要洗：
- 洗衣机：30分钟
- 烘干机：40分钟
- 折叠：20分钟

**串行执行**：必须等 Ann 的所有步骤全部完成，才能开始 Brian 的——总耗时 = 4 × (30+40+20) = **6 小时**

**流水线执行**：Ann 的衣服进了烘干机，Brian 的就可以开始洗——总耗时约 **3.5 小时**

**流水线的本质：各阶段的硬件资源在不同时刻被不同任务使用，资源利用率提高**。

### 1.3 为什么用流水线？

1. **提高吞吐量（Throughput）**：单位时间内完成更多指令
2. **提高资源效率**：功能部件（ALU、内存接口等）利用率更高
3. **降低 CPU Time**：是降低 CPI 的主要手段

> 注意：流水线**不能减少单条指令的执行延迟**，甚至可能略有增加（因为加了流水线寄存器开销）。

## 二、经典五阶段流水线

### 2.1 MIPS 五阶段流水线

标准的 MIPS 流水线将指令执行分为 5 个阶段：

| 阶段 | 缩写 | 工作内容 |
|------|------|----------|
| **取指** | IF (Instruction Fetch) | 从 PC 地址取出指令，PC+4 |
| **译码/寄存器读** | ID (Instruction Decode) | 解码指令，读取寄存器操作数，冒险检测 |
| **执行** | EX (Execute) | ALU 运算，分支目标地址计算 |
| **访存** | MEM (Memory Access) | 读写数据内存（Load/Store） |
| **写回** | WB (Write Back) | 将结果写回寄存器堆 |

**流水线寄存器（Pipeline Registers）**：每两个相邻阶段之间有一组寄存器，用于保存当前阶段的中间结果，传递给下一阶段。
- IF/ID、ID/EX、EX/MEM、MEM/WB

### 2.2 理想流水线的性能

若各阶段**完全平衡**（每阶段耗时相同），则：

$$\text{流水线 CPI} = 1$$

$$\text{时钟周期} = \frac{\text{未流水线时钟周期}}{\text{流水线阶段数}}$$

$$\text{理想加速比} = \text{流水线阶段数} = n$$

与**单周期实现**相比（CPI=1，但时钟周期很长）：
- 流水线的时钟周期 = 单周期时钟周期 / 5
- CPI 都是 1
- 所以流水线速度约为单周期的 **5 倍**

与**多周期实现**相比（时钟周期短但 CPI=5）：
- 流水线时钟周期 ≈ 多周期时钟周期（相同）
- CPI 降为 1（多周期 CPI=5）
- 所以流水线速度约为多周期的 **5 倍**

### 2.3 为什么不做 50 阶段的流水线？

理论上阶段越多加速比越大，但实际上有两个重要限制：

**①逻辑不可无限细分**：某些运算本身不能分成更细的逻辑阶段（比如乘法器就是乘法器）。

**②流水线寄存器的开销不可忽略**：
- 流水线寄存器（Latch）需要面积和时间
- 每个阶段的时钟周期必须 > 锁存延迟 + 时钟偏斜（Clock Skew）
- 现代深度流水线（10~20阶段）中，一个流水级只有 10~20 个门的逻辑深度，此时锁存延迟占比显著

**现实案例**：Intel Pentium 4 有 20+ 级流水，达到了 >1GHz 的频率，但也带来了复杂的冒险控制和大量流水线气泡。

## 三、流水线冒险（Pipeline Hazards）

> **冒险（Hazard）**：流水线中阻止下一条指令在预定时钟周期执行的条件。

冒险分三类：**结构冒险、数据冒险、控制冒险**。

解决冒险的最简单办法：**流水线停顿（Stall）**——在流水线中插入气泡（Bubble），让指令等待。但停顿会降低性能。

**有停顿时的 CPI**：

$$CPI = \text{理想CPI} + \text{结构停顿} + \text{数据停顿} + \text{控制停顿}$$

$$\text{加速比} = \frac{\text{阶段数}}{1 + \text{每条指令平均停顿周期数}}$$

---

## 四、结构冒险（Structural Hazard）

### 4.1 定义与原因

**结构冒险**：两条或多条指令在同一时钟周期争用**同一硬件资源**，导致冲突。

**典型场景**：
- 取指和 Load/Store 都需要访问内存（若只有一个内存端口）
- 寄存器堆同一端口被多条指令同时读写
- 浮点乘法器未被流水化，占用多个周期

### 4.2 解决方法

| 方法 | 说明 |
|------|------|
| **硬件复制** | 分离指令Cache和数据Cache（主要解法）|
| **双边沿读写（Double Bump）** | 在时钟上升沿写、下降沿读寄存器，支持同周期写后读 |
| **插入停顿** | 检测到冲突时停顿一个周期，代价是性能下降 |

**分离指令Cache和数据Cache**是最常用的解法：
- IF 访问指令 Cache，MEM 访问数据 Cache
- 两者可以在同一周期并行工作
- 代价：总内存带宽需求翻倍

### 4.3 未完全流水化的功能部件

某些硬件为什么允许有结构冒险（不完全流水化）？
1. **降低成本**：完全流水化的浮点单元需要大量门电路
2. **降低延迟**：流水化会增加每级的开销（寄存器延迟），非流水化版本对于频率低的操作可能反而更快

**例子**：非流水化浮点乘法器（6个周期），若 FP 乘法占 14%，均匀分布时几乎无性能损失；即使最坏情况下，实际测量执行时间增加也不超过 **3%**。

## 五、数据冒险（Data Hazard）

### 5.1 定义与原因

**数据冒险**：后续指令需要使用前一条指令的计算结果，但该结果尚未写回寄存器。

这是因为流水线**改变了读写操作的相对顺序**，使得"应该先写后读"的操作变成了"先读（旧值）后写（新值）"。

**例子**：
```
DADD  R1, R1, R3    # 第1周期取指
DSUB  R4, R1, R5    # 第2周期取指，此时R1还没写完！
AND   R6, R1, R7    # R1仍未写完
OR    R8, R1, R9
XOR   R10, R1, R11
```

### 5.2 三类数据冒险

| 类型 | 全称 | 条件 | 频率 |
|------|------|------|------|
| **RAW（先写后读）** | Read After Write | 指令B读取指令A要写的寄存器 | **最常见** |
| **WAW（先写后写）** | Write After Write | 指令B写入与指令A相同的寄存器 | 较少（仅多周期流水线中出现）|
| **WAR（先读后写）** | Write After Read | 指令B写入指令A要读的寄存器 | **在五阶段顺序流水线中不会出现** |

**注意**：在简单的顺序5阶段流水线中，指令按序完成，WAR不会发生（读总在写之前完成）。WAW 也只在多周期功能部件（如浮点流水线）中出现。

### 5.3 RAW 冒险的解决：数据前递（Forwarding）

**停顿法**：等待 WB 写完后再让后续指令读——慢，要停几个周期。

**数据前递（Forwarding，也叫 Bypass 或 Short-Circuiting）**：

> 核心思想：结果虽然还没写回寄存器堆，但它已经存在于某个流水线寄存器中了——直接把它"转发"给需要的指令！

**前递路径**：
- `EX/MEM 寄存器 → ALU 输入`：当前指令需要上一条指令的 ALU 结果
- `MEM/WB 寄存器 → ALU 输入`：当前指令需要两条前的指令结果
- `MEM/WB.LMD → 数据内存输入`：Load 指令的结果转发

**硬件实现**：在数据通路中添加多路选择器（MUX），根据冒险检测逻辑选择是从寄存器堆读取还是从流水线寄存器转发。

### 5.4 Load-Use 冒险（不能被前递完全解决）

**Load-Use 冒险**：Load 指令在 MEM 阶段才能从内存读出数据，而下一条指令在 EX 阶段就需要这个数据。

```
LW  R1, 0(R2)    # MEM 阶段才有数据
SUB R4, R1, R6   # EX 阶段就需要 R1，比 LW 的 MEM 早一个周期！
```

即使有前递，也**必须插入 1 个停顿周期**（Load Delay Slot）。

**检测逻辑**：
```
IF (ID/EX.MemRead AND ((ID/EX.RegisterRt == IF/ID.RegisterRs) OR (ID/EX.RegisterRt == IF/ID.RegisterRt)))
    stall pipeline
```

**性能影响**：
- 假设 30% 是 Load 指令，其后跟依赖指令的概率是 50%
- CPI = 1 + 0.30 × 0.50 × 1 = **1.15**
- 性能下降约 15%

**编译器优化**：指令重排（Instruction Reordering）——编译器把 Load 后面的 1 个无关指令提前填充到 Load 后面，避免停顿：

```
# 慢代码（有Load停顿）       # 快代码（消除停顿）
LW  Rb, b                    LW  Rb, b
LW  Rc, c                    LW  Rc, c
ADD Ra, Rb, Rc               LW  Re, e      ← 提前
SW  a, Ra                    ADD Ra, Rb, Rc
LW  Re, e                    LW  Rf, f      ← 提前
LW  Rf, f                    SW  a, Ra
SUB Rd, Re, Rf               SUB Rd, Re, Rf
SW  d, Rd                    SW  d, Rd
```

### 5.5 WAW 冒险（多周期浮点流水线中）

发生条件：指令 B 完成（写回）比指令 A 更早，导致 B 的结果被 A 的结果**覆盖**（顺序被打乱）。

**解决方法**：
1. 在 ID 阶段检测到 WAW，停顿后发的指令
2. 或取消先发指令的 WB 阶段（直接用后发指令的结果覆盖）

## 六、控制冒险（Control Hazard）

### 6.1 问题的本质

**控制冒险**：分支指令的目标地址和跳转条件在流水线中**来不及在 IF 阶段之前算出**，导致不知道下一条指令应该取哪里的。

对于五阶段流水线：
- 分支条件在 **EX 阶段**才能确定
- 分支目标地址在 **EX 阶段**才能算出
- 这意味着取指（IF）时，要到 3 个周期后才知道取的对不对

**性能影响计算**：
- 分支频率 30%，每次分支惩罚 3 个周期
- CPI = 1 + 30% × 3 = **1.9**
- 性能接近理想的**一半**！

### 6.2 方案一：冲刷流水线（Flush / Insert Stalls）

每遇到分支，就停顿 3 个周期，等分支结果确定后再取指。

**优点**：简单，硬件实现容易  
**缺点**：性能损失严重（如上所述降低到理想的 50%）

### 6.3 方案二：前移分支判断（Move Branch Computation Forward）

**优化**：将分支条件判断和目标地址计算**从 EX 阶段提前到 ID 阶段**：
- 在 ID 阶段增加比较器，直接比较寄存器值
- 在 ID 阶段计算分支目标地址

**效果**：分支惩罚从 3 个周期减少到 **1 个周期**。

### 6.4 方案三：延迟分支（Delayed Branch）

**MIPS 的实际解法**：  
既然分支后必然有 1 个周期的延迟，不如**规定这个延迟槽位一定会执行**（无论分支跳或不跳），让编译器把有用的指令填进去：

```
BNEZ  R1, Label      ← 分支指令
ADD   R2, R3, R4     ← 延迟槽位（Branch Delay Slot），总会执行
                     ← 分支目标从这里开始
```

**编译器如何填充延迟槽**（填充率通常能达到 60%~70%）：

**策略 A**：从分支前寻找独立指令移入延迟槽（最常用，总是安全）

**策略 B（循环前移）**：把第一次迭代的指令提前到循环外
```
# 原始代码                       # 重排后（B填充策略）
Loop: LW    R2, 0(R1)           LW  R2, 0(R1)     # 循环前，第一次迭代
      ADD   R3, R2, R4          Loop: ADD  R3, R2, R4
      SW    R3, 0(R1)                 SW   R3, 0(R1)
      SUB   R1, R1, #4                ...
      BNEZ  R1, Loop                  SUB  R1, R1, #4
                                      BNEZ R1, Loop
                                      LW   R2, 0(R1) ← 延迟槽，下次迭代预取
```

**策略 C（从目标移入延迟槽）**：从分支目标取一条指令移入延迟槽  
- 只在预测分支**经常跳**的情况下适用
- 若分支不跳，需要该指令无副作用（或取消执行）

### 6.5 预测不跳（Predict-Not-Taken）

另一种硬件方法：**始终假设分支不跳**，继续取后续指令。

- 若预测正确（不跳）：无性能损失
- 若预测错误（实际跳）：冲刷已取的指令，重新从目标地址取指，付出延迟代价

**MIPS R4000 使用这种方法**，因为硬件最简单。

## 七、多周期浮点流水线（Multi-Cycle FP Operations）

### 7.1 为什么需要多周期 FP 操作？

浮点运算（加法、乘法、除法、开方）**复杂度远高于整数运算**，无法在一个时钟周期内完成。两种方案：

1. 用慢时钟（所有操作都能1周期完成）——整体性能太差
2. **允许浮点单元有更长的延迟**（多周期执行），同时可能有多个浮点功能部件

### 7.2 MIPS 扩展流水线结构

在五阶段整数流水线基础上，增加独立的浮点功能部件：
- **FP 加法器（A）**：4 个周期，流水化
- **FP 乘法器（M）**：7 个周期，流水化
- **FP 除法器（DIV）**：未流水化（非流水化）

**两个重要术语**：

| 术语 | 定义 |
|------|------|
| **延迟（Latency）** | 产生结果的指令与使用结果的指令之间必须间隔的周期数 |
| **发射间隔（Initiation Interval）** | 同一功能部件连续发射两条指令之间的最小间隔周期数 |

- 完全流水化的部件：发射间隔 = 1（每周期都可以接受新指令）
- 未流水化的部件：发射间隔 = 延迟 + 1

### 7.3 多周期流水线引入的新冒险

| 冒险类型 | 原因 |
|----------|------|
| **结构冒险（寄存器写端口）** | 多条指令可能在同一周期都要写回寄存器 |
| **RAW 冒险加剧** | 浮点延迟长（7周期），停顿更频繁 |
| **WAW 冒险** | 乱序完成导致后发指令先完成，覆盖先发指令的结果 |
| **异常处理复杂** | 乱序完成使精确异常（Precise Exception）难以实现 |

**解决写端口冲突**：
- 方法1：增加写端口数量（硬件成本高，不推荐）
- 方法2：用移位寄存器追踪哪些周期有写操作，检测冲突并在 ID 阶段插入停顿（推荐）

## 八、真实案例：MIPS R4000 流水线

MIPS R4000 采用了更深的 **8 阶段流水线**（超级流水，Superpipelining）：

| 阶段 | 描述 |
|------|------|
| **IF** | 取指前半段：PC 选择，启动 Cache 访问 |
| **IS** | 取指后半段（Cache 访问需要两个周期）|
| **RF** | 译码+寄存器读取，冒险检测，Cache 命中检测 |
| **EX** | 执行：地址计算，ALU，分支目标和条件计算 |
| **DF** | 数据取第一周期 |
| **DS** | 数据取第二周期 |
| **TC** | Cache 标签检查（判断 Cache 是否命中）|
| **WB** | Load 和 R 型指令写回 |

**特点**：
- **Load 延迟 2 个周期**：数据在 TC 阶段才能确认正确，所以需要 2 个停顿周期（而不是 1 个）
- **分支延迟 3 个周期**（包含 1 个分支延迟槽）：分支在 EX 阶段解析，共有 3 个周期延迟
- 采用 **预测不跳（Predict-Not-Taken）**

## 九、流水线性能总结

| 实现方式 | CPI | 时钟周期 | 性能评估 |
|----------|-----|----------|----------|
| 单周期 | 1 | 最长路径（约5×每阶段）| 慢 |
| 多周期 | ~5 | 最短阶段时间 | 中等 |
| 五阶段流水线（无停顿） | 1 | 最短阶段时间 | 快约5× |
| 五阶段流水线（有停顿） | > 1 | 最短阶段时间 | 中快 |

**现实中的流水线 CPI 计算**：

$$CPI = 1 + \text{结构停顿} + \text{数据停顿} + \text{控制停顿}$$

**各类停顿的来源与优化方向**：

| 停顿来源 | 优化技术 |
|----------|----------|
| 结构冒险 | 分离 I/D-Cache，增加寄存器端口，双边沿读写 |
| RAW 数据冒险 | 数据前递（Forwarding / Bypass） |
| Load-Use 冒险 | 编译器指令重排，或硬件停顿 |
| WAW 冒险 | ID 阶段检测并停顿 |
| 控制冒险 | 延迟分支，分支预测，提前计算分支条件 |

## 十、总结

流水线是**提高处理器性能的基石技术**，理解流水线的设计是后续所有高级体系结构技术（超标量、乱序执行、动态调度）的基础。

**核心要点**：

1. **理想加速比 = 流水线阶段数**，但实际因冒险而下降
2. **三类冒险**：结构 / 数据 / 控制，各有不同的检测和解决方案
3. **数据前递（Forwarding）** 能消除大部分 RAW 停顿，但对 Load-Use 无效（必须停顿 1 周期）
4. **延迟分支** 是 MIPS 处理控制冒险的经典方法，需要编译器配合填充延迟槽
5. **更深的流水线**（如 R4000 的 8 级）可以提高时钟频率，但增加了冒险解决的复杂度和延迟惩罚

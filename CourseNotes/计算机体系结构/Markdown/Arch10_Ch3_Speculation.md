## 一、Tomasulo 算法的不足（Drawbacks）

前一章讲解的 Tomasulo 算法实现了乱序执行，但存在以下问题：

### 1.1 公共数据总线（CDB）瓶颈
所有功能单元的结果都通过 CDB 广播，每个时钟周期只能有**一个结果**广播。当多个 FU 同时完成时，其余 FU 必须等待 → **CDB 成为性能瓶颈**。

### 1.2 非精确异常（Non-precise Interrupts）
乱序执行导致指令**完成顺序与程序顺序不同**。如果一条指令触发异常（如除零），此时它之后的某些指令可能已经执行完毕并写回寄存器 → 无法精确地在异常发生点恢复处理器状态 → **不支持精确中断**。

### 1.3 跨基本块的重叠执行问题
Tomasulo 可以让整数指令跑在浮点指令前面（部分重叠基本块）。但**分支解决前，后继基本块不能安全地提交结果** → 分支预测结果不确定时，投机执行的指令结果无法提交。

## 二、硬件投机执行（Hardware-based Speculation）★

### 2.1 核心思想

**投机执行（Speculation）** = **动态分支预测 + 乱序执行 + 顺序提交（In-Order Commit）**

三个关键思想：
1. **动态分支预测**：选择下一步执行哪条指令（预测分支方向）
2. **投机执行**：在控制依赖解决前就执行后续指令（"赌一把"）
3. **动态调度**：处理不同基本块指令组合的调度问题

**数据流执行（Data Flow Execution）**：操作数就绪后立即执行，不等待程序顺序。

### 2.2 关键设计原则

**将执行完成（Execution Complete）与提交（Commit / Instruction Commitment）解耦：**

- 执行完成的结果**暂存在缓冲区中**，而非直接写入寄存器文件或内存
- 只有当确认一条指令**不再是投机的**（分支确定、无异常），才**提交（Commit）** 结果到体系结构状态
- 执行可以**乱序**，但提交必须**按照程序顺序**（In-Order Commit）

这样就能实现：
- ✅ 投机执行（预测正确时：无损失）
- ✅ 精确异常（提交时处理异常，顺序确定）
- ✅ 分支预测错误后回滚（只需刷新缓冲区）

## 三、重排序缓冲区（Reorder Buffer, ROB）★★

### 3.1 ROB 的引入

ROB 是在 Tomasulo 算法基础上添加的关键新结构，用于**缓存投机执行的结果**，直到可以安全提交。

**与原始 Tomasulo 的区别**：

| 特性 | 原始 Tomasulo | 带 ROB 的 Tomasulo |
|------|--------------|-------------------|
| 结果写入 | 直接写寄存器文件 | 先写 ROB，提交时才写寄存器 |
| 寄存器重命名 | 保留站（RS）负责 | ROB 负责（RS 只存操作码和操作数）|
| 精确异常 | ❌ 不支持 | ✅ 支持 |
| 投机执行 | ❌ 受限 | ✅ 支持 |

**ROB 的双重角色**：
1. **存储投机结果**：保存已执行但未提交的指令结果
2. **操作数来源**：指令执行完到提交之间，ROB 可以作为操作数来源（类似扩展的寄存器堆）

### 3.2 ROB 条目结构

每个 ROB 条目（Entry）包含以下字段：

| 字段 | 说明 |
|------|------|
| **指令类型（Instruction Type）** | 分支/存储/运算/载入 |
| **目的字段（Destination）** | 结果写入的寄存器编号或内存地址 |
| **值字段（Value）** | 执行结果（执行完成后填入）|
| **就绪位（Ready）** | 指令是否已执行完成 |
| **异常向量（Exception Vector）** | 如果指令触发异常，记录异常信息 |

ROB 是**循环队列（Circular FIFO）**：
- 新发射的指令从**尾部（Newest）** 插入
- 从**头部（Oldest）** 按顺序提交

## 四、带 ROB 的投机 Tomasulo 算法：四个步骤 ★★

### 步骤一：发射（Issue / Dispatch）

- 从 FP 操作队列取指令
- 若**保留站（RS）空闲** 且 **ROB 有空槽**：
  - 发射指令到 RS
  - 发送操作数（可能是寄存器值或 ROB 编号）
  - 在 ROB 中分配一个条目，记录目的寄存器 → 对应 ROB 编号
  - 更新寄存器状态：该目的寄存器的"提供者"改为对应的 ROB 条目编号

### 步骤二：执行（Execute / EX）

- 当**两个操作数都就绪**时执行
- 若操作数未就绪：**监听 CDB**，等待广播
- 两个操作数都在保留站中就绪后执行
- 检查 RAW 冒险（由数据流控制，通过 ROB 编号追踪）

### 步骤三：写结果（Write Result / WB）

- 通过 **CDB 广播结果** 到所有等待的保留站和 ROB 条目
- 将 ROB 对应条目的就绪位置 1，填入结果值
- 释放保留站（RS 不再需要保存结果，结果由 ROB 保管）

### 步骤四：提交（Commit）

当 ROB **头部（Oldest）** 的指令就绪时：

**① 普通非分支指令（寄存器写操作）**：
- 将 ROB 中的值写入目的寄存器
- 从 ROB 中移除该条目
- 若该寄存器的"提供者"仍是本 ROB 条目，则清除（寄存器值已是最新）

**② STORE 指令**：
- 将值写入**内存**（而非寄存器）
- 从 ROB 中移除

**③ 分支预测正确**：
- 正常提交，该分支指令的 ROB 条目移除

**④ 分支预测错误（Mispredicted Branch）**：
- **刷新（Flush）整个 ROB**（删除所有投机指令的结果）
- 从分支的**实际后继地址**重新取指执行
- 这个操作有时称为"**毕业（Graduation）**"中止

## 五、ROB 执行示例

以下面 6 条 FP 指令为例（2个周期的流水线内存访问）：

```asm
LD    F6, 34(R2)    ; 1: 从内存加载
LD    F2, 45(R3)    ; 2: 从内存加载
MULD  F0, F2, F4    ; 3: F2 × F4 → F0
SUBD  F8, F2, F6    ; 4: F2 - F6 → F8
DIVD  F10, F0, F6   ; 5: F0 ÷ F6 → F10
ADDD  F6, F8, F2    ; 6: F8 + F2 → F6
```

执行过程中的 ROB 状态变化（关键时刻）：

**初始发射后**：
- ROB 中按程序顺序排列 6 个条目
- 每条指令的目的寄存器映射到对应 ROB 条目编号
- MULD（条目3）的操作数：一个来自 ROB（等 LD F2 完成），另一个来自寄存器 F4

**LD 指令完成后**：
- LD F6 完成 → ROB1 就绪，值 = M[34+R2]
- LD F2 完成 → ROB2 就绪，值 = M[45+R3]
- SUBD 的操作数可以从 ROB1/ROB2 取值（CDB 转发）

**MULD 执行**（ROB3，操作数 = ROB2 中的值，R(F4)）：
- SUBD 的操作数变成 ROB2 的值 和 M[34+R2]

**关键**：注意 ADDD 写的是 F6（原 LD F6 的目标），形成 WAW 冒险 → ROB 通过维护最新的 ROB 编号映射**自动解决 WAW/WAR 冒险**。

## 六、内存消歧（Memory Disambiguation）★

### 6.1 问题描述

当程序中有先 Store 后 Load 的序列：

```asm
ST  0(R2), R5   ; 将 R5 存入地址 0(R2)
LD  R4,  0(R3)  ; 从地址 0(R3) 加载到 R4
```

**问题**：能否提前执行 LD，不等 ST 完成？

- 如果 `0(R2) ≠ 0(R3)`：两者无依赖，LD 可以先执行 → 提高性能
- 如果 `0(R2) == 0(R3)`：存在 RAW 冒险（LD 必须读取 ST 写入的值）→ 不能提前执行

**挑战**：ST 的地址可能依赖一个长计算（如除法），地址很晚才知道。如果必须等到 ST 地址确定才能执行 LD，会损失大量 ILP。

### 6.2 解决方案：存储队列（Store Queue）

**硬件支持**：维护一个**存储队列（Store Queue）**，按程序顺序跟踪所有未提交的 Store 指令（地址 + 数据）。

**Load 执行时的检查流程**：

1. 发射 Load 时，记录当前 Store 队列的"头部位置"（知道哪些 Store 在 Load 之前）
2. 当 Load 地址确定后，**在 Store 队列中做关联查询（Associative Lookup）**：
   - 若有在 Load 之前的 Store 尚未确定地址 → **等待（Stall Load）**，不能冒进
   - 若 Load 地址与某个早期 Store 地址**相同**（RAW 冒险）：
     - Store 值已知 → 直接从队列中取值（Store-to-Load Forwarding）
     - Store 值未知 → 返回该 Store 的 ROB 编号，等待结果
   - 若无地址冲突 → 向内存发送请求，正常执行

3. Store 提交时按程序顺序写入内存 → 自动避免 WAR/WAW 冒险

## 七、精确异常支持

ROB 实现精确异常的原理：

1. 异常信息（异常向量）**存储在 ROB 条目中**，并不立即处理
2. 当该指令到达 ROB **头部（最老的指令）** 且就绪时：
   - 若有异常 → 此时**所有更早的指令都已提交**，状态精确
   - 处理异常：保存精确的程序计数器（PC），调用异常处理程序
3. 投机指令（该指令之后的）的结果**尚未提交** → 丢弃 ROB 中的结果即可

**关键**：顺序提交（In-Order Commit）保证了"精确"——即异常发生时，比异常指令更早的所有指令都已完成，更晚的指令一条都未修改架构状态。

## 八、总结：带 ROB 的投机 Tomasulo

### 整体架构

```
         指令取指/发射队列
                ↓
    ┌──────────────────────────┐
    │      保留站（RS）         │  ← 存储操作码和操作数（只到执行完成）
    └──────────────────────────┘
                ↓ 执行
    ┌──────────────────────────┐
    │     重排序缓冲区（ROB）    │  ← 存储执行结果（按程序顺序提交）
    └──────────────────────────┘
                ↓ 提交（In-Order）
         寄存器堆 / 内存
```

### 关键性质对比

| 特性 | Tomasulo（无ROB）| 投机 Tomasulo（有ROB）|
|------|-----------------|----------------------|
| 乱序执行 | ✅ | ✅ |
| 分支投机 | ❌ | ✅ |
| 精确异常 | ❌ | ✅ |
| 分支误预测恢复 | 困难 | ✅ 刷新ROB |
| 内存顺序 | 有问题 | ✅ Store Queue |

### 核心思想一句话总结

> **"执行可以乱，提交必须顺"（Execute Out-of-Order, Commit In-Order）** ——这是支持投机执行、精确异常、分支预测的基础。

> **下一章**将介绍如何将这些机制扩展到每周期发射**多条**指令的**超标量（Superscalar）** 和 **VLIW** 处理器——进一步提高指令级并行度（ILP）。

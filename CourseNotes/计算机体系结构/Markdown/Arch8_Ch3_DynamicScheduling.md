## 一、概述：什么是指令级并行？

### 1.1 流水线 CPI 回顾

$$\text{Pipeline CPI} = \text{理想CPI} + \text{结构冒险停顿} + \text{数据冒险停顿} + \text{控制冒险停顿}$$

降低 CPI 的方向：减少各类冒险引起的停顿。

**指令级并行（ILP, Instruction-Level Parallelism）**：指令之间潜在的可以重叠执行的并行性。

### 1.2 基本块中 ILP 的局限

- **基本块（Basic Block）**：没有跳转入的直线代码段，也没有跳转出（除了末尾）
- 动态分支频率约 15%~25% → 两次分支之间平均只有 **4~7 条指令**
- 基本块内指令之间还可能互相依赖 → 实际可并行的指令更少

因此，要获得显著的 ILP，必须**跨越基本块边界**（通过循环展开、分支预测等手段）。

## 二、数据相关与冒险

### 2.1 三种数据相关

设指令 A 在 B 之前执行：

| 类型 | 名称（编译器术语）| 流水线冒险 | 本质 |
|------|-----------------|------------|------|
| 先写后读（A写Rx，B读Rx）| **真相关（True Dependence）**| RAW（Read After Write）| 数据流依赖 |
| 先读后写（A读Rx，B写Rx）| **反相关（Anti-dependence）**| WAR（Write After Read）| 名称重用 |
| 先写后写（A写Rx，B写Rx）| **输出相关（Output dependence）**| WAW（Write After Write）| 名称重用 |

**关键区分**：
- **RAW** 是真正的数据流依赖，**必须**按序完成（B 需要 A 产生的值）
- **WAR 和 WAW** 是**名称依赖（Name Dependence）**，只是因为使用了相同的寄存器名，并无实际数据流 → **可通过寄存器重命名消除**

### 2.2 数据依赖的重要性

数据依赖决定了：
1. 冒险发生的**可能性**
2. 结果必须计算的**顺序**
3. 可利用并行度的**上界**

### 2.3 控制依赖

每条指令都控制依赖于某些分支指令。控制依赖**不必严格保留**，只需保证：
- **异常行为（Exception Behavior）**不变：不能因为指令重排引入新的异常
- **数据流（Data Flow）**正确：不能因重排改变实际到达某指令的操作数来源

## 三、编译器基本技术：循环展开

### 3.1 FP 循环示例

```mips
Loop:  LD    F0, 0(R1)    ; 载入向量元素
       ADDD  F4, F0, F2  ; 加上标量 F2
       SD    0(R1), F4   ; 存储结果
       SUBI  R1, R1, 8   ; 指针递减
       BNEZ  R1, Loop    ; 循环
       NOP               ; 延迟槽
```

**延迟（Latency）**（寄存器-寄存器之间的气泡数）：
- FP ALU → FP ALU：3 周期停顿
- FP ALU → Store：2 周期停顿
- Load → FP ALU：1 周期停顿

不调度时，每次迭代需要约 **10 个时钟周期**（含停顿）。

调度后（利用延迟槽），降至约 **6 个周期/迭代**。

### 3.2 循环展开（Loop Unrolling）

将循环体展开 4 次，相当于一次处理 4 个迭代：

**朴素展开**（含停顿）：14+ 周期 = 约 **6.5 周期/迭代**

**优化展开**（重排指令，消除停顿）：
```mips
Loop:  LD    F0,  0(R1)
       LD    F6,  -8(R1)
       LD    F10, -16(R1)
       LD    F14, -24(R1)
       ADDD  F4,  F0,  F2   ; 利用了 Load 的延迟
       ADDD  F8,  F6,  F2
       ADDD  F12, F10, F2
       ADDD  F16, F14, F2
       SD    0(R1),   F4
       SD    -8(R1),  F8
       SUBI  R1, R1,  #32
       SD    +16(R1), F12
       BNEZ  R1, LOOP
       SD    8(R1),   F16   ; 8-32=-24，延迟槽
```

共 **14 个时钟周期处理 4 次迭代 = 3.5 周期/迭代**（接近两倍提速）。

**注意**：编译器重排指令时需满足：
- 移动 Store 越过 SUBI 是安全的（调整了地址偏移）
- Load 移到 Store 前需要确认不会读取到未更新的地址

## 四、为什么需要动态调度？

### 4.1 静态调度的局限

**例1（RAW 冒险导致无关指令被阻塞）**：
```mips
DIVD  F0, F2, F4   ; DIVD 延迟 40 周期
ADDD  F10, F0, F8  ; 等待 DIVD，停顿
SUBD  F12, F8, F14 ; 与 DIVD 无关，但被迫等待
```

问题：`SUBD` 与 `DIVD` 无关，却因为程序顺序被阻塞在 `ADDD` 之后无法执行。

**例2（结构冒险 + 名称依赖）**：
```mips
DIVD  F2, F2, F4
ADDD  F10, F0, F8  ; FP 加法器未流水化，占用 2 周期
ADDD  F12, F0, F4  ; 等待加法器
MULD  F16, F14, F4 ; 本可提前执行
```

**核心需求**：允许**停顿处后面的独立指令越过停顿继续执行**。

### 4.2 动态调度的关键思想

> 允许停顿后面的无关指令**继续前进（proceed）**，实现**乱序执行（Out-of-Order Execution）**。

**实现方式**：将 ID 阶段拆分为两个步骤：
1. **Issue（发射）**：解码指令，检查结构冒险
2. **Read Operands（读操作数）**：等待数据冒险消除后，读取操作数

## 五、Scoreboard 算法（CDC 6600）

### 5.1 历史背景

**Scoreboard（记分板）** 是 **CDC 6600**（1964年，世界第一台超级计算机）使用的动态调度机制。

### 5.2 Scoreboard 的目标与特点

- **顺序发射（In-Order Issue）**：指令按程序顺序发射
- **乱序执行（Out-of-Order Execution）**
- **乱序完成（Out-of-Order Completion）**
- 当有足够资源且无数据依赖时，尽早执行指令

### 5.3 流水线阶段（IF, IS, RO, EX, WB）

| 阶段 | 名称 | 描述 |
|------|------|------|
| IF | Instruction Fetch | 取指，与简单流水线相同 |
| IS | Issue（发射）| 解码，检查**结构冒险**和 **WAW 冒险**；若有，停顿等待 |
| RO | Read Operands（读操作数）| 等待所有源操作数可用（无 RAW），然后读取 |
| EX | Execute（执行）| 功能部件执行，完成后通知 Scoreboard |
| WB | Write Back（写回）| Scoreboard 检查 **WAR 冒险**，若有则停顿 |

### 5.4 Scoreboard 的三个数据结构

#### ① 指令状态表（Instruction Status）
记录每条指令当前处于哪个阶段（IS/RO/EX/WB）。

#### ② 功能部件状态表（Functional Unit Status）
每个功能部件（整数ALU、FP加法器、FP乘法器、除法器等）维护：

| 字段 | 含义 |
|------|------|
| Busy | 该功能部件是否忙碌 |
| Op | 正在执行的操作类型 |
| Fi | 目标寄存器 |
| Fj, Fk | 源寄存器 |
| Qj, Qk | 产生 Fj/Fk 的功能部件（若还未就绪）|
| Rj, Rk | Fj/Fk 是否已就绪（可以读取）|

#### ③ 寄存器结果状态表（Register Result Status）
记录每个寄存器**将由哪个功能部件写入**（若无待写则为空）。

### 5.5 各阶段判断条件

**Issue（发射）**：满足以下两个条件才能发射：
1. 对应功能部件**未被占用**（无结构冒险）
2. 没有其他已发射指令的目标寄存器与本指令相同（无 **WAW 冒险**）

**Read Operands（读操作数）**：
- 等待所有源寄存器不再是任何未完成指令的目标寄存器（无 **RAW 冒险**）

**Write Back（写回）**：
- Scoreboard 检查：是否有指令的**源操作数是本指令的目标**且尚未读取（**WAR 冒险**）
- 若有，停顿写回，等待那条指令完成 RO 阶段后再写

### 5.6 Scoreboard 示例

```mips
LD     F6, 34(R2)
LD     F2, 45(R3)
MULTD  F0, F2, F4   ; 10 周期
SUBD   F8, F6, F2   ; 2 周期
DIVD   F10, F0, F6  ; 40 周期
ADDD   F6, F8, F2   ; 2 周期
```

执行流程（关键步骤）：
- `MULTD` 发射后等待 `LD F2` 完成（RAW）
- `SUBD` 可以独立执行（F6 和 F2 已就绪）
- `ADDD` 需等待 `SUBD` 完成，同时目标 F6 有 WAR 风险（`DIVD` 需要 F6）
- `DIVD` 等待 `MULTD` 完成（RAW on F0）

### 5.7 Scoreboard 的局限

1. **ILP 不足**时，Scoreboard 帮助有限（受窗口大小限制）
2. **结构冒险**：功能部件数量少时频繁停顿
3. **WAR 和 WAW 冒险**：Scoreboard 用停顿解决（不如 Tomasulo 的寄存器重命名高效）
4. **窗口不能跨越分支**（仅在基本块内调度）

## 六、Tomasulo 算法（IBM 360/91）

### 6.1 历史背景与动机

**IBM 360/91**（1966年）设计时：
- 浮点寄存器只有 4 个 → 编译器难以有效调度
- 工程师 **Robert Tomasulo** 发明了一种硬件寄存器重命名方案，使处理器能自主发现并利用 ILP

**为什么 IBM 360/91 的设计影响深远？**
- Alpha 21264、HP PA-8000、MIPS R10000、Pentium III、PowerPC 604 等都是其思想的继承者！

### 6.2 Tomasulo 算法核心思想

**四大核心机制**：

1. **保留站（Reservation Station, RS）**：每个功能部件有自己的等待队列，存放挂起的操作数和操作码
2. **寄存器重命名（Register Renaming）**：寄存器名被替换为**保留站号或操作数值本身**，消除 WAR/WAW 冒险
3. **公共数据总线（Common Data Bus, CDB）**：功能部件完成后，结果**广播**给所有等待该结果的保留站
4. **乱序发射到保留站**：指令发射后不等待操作数，先进保留站等待

### 6.3 Tomasulo 的组织结构

```
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│   指令队列（FP Op Queue）                                     │
│        ↓ 发射（Issue）                                       │
│   ┌─────────────────────────────────────────────────────┐   │
│   │  保留站（Reservation Stations）                      │   │
│   │  - Add RS（加法/减法）                               │   │
│   │  - Mult/Div RS（乘除法）                             │   │
│   └─────────────────────────────────────────────────────┘   │
│        ↕ 操作数通过 CDB 传递                                 │
│   ┌──────────────┐   ┌──────────────┐   ┌───────────────┐  │
│   │ 加法功能部件  │   │ 乘/除功能部件│   │  Load/Store   │  │
│   └──────────────┘   └──────────────┘   │   缓冲区       │  │
│        ↓                    ↓           └───────────────┘  │
│   ══════════ 公共数据总线（CDB）══════════                   │
│   ┌─────────────────────────────────────────────────────┐   │
│   │            浮点寄存器文件（FP Register File）         │   │
│   └─────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

### 6.4 保留站字段说明

每个保留站项包含：

| 字段 | 含义 |
|------|------|
| **Op** | 要执行的操作 |
| **Vj, Vk** | 源操作数的**值**（已就绪时存储）|
| **Qj, Qk** | 产生操作数的**保留站编号**（未就绪时存储，0表示已就绪）|
| **A** | 内存地址计算相关信息（Load/Store 用）|
| **Busy** | 该保留站是否被占用 |

**Register Result Status（寄存器结果状态）**：记录哪个保留站将写入某个寄存器（若有未完成写入的话）。

### 6.5 Tomasulo 三个阶段

#### ① Issue（发射）

从 FP 指令队列取指令，若有**空闲保留站**则发射（无结构冒险）：
- 操作数**已就绪** → 将值写入保留站 V 字段
- 操作数**未就绪** → 在保留站 Q 字段记录将产生该操作数的保留站号
- 更新寄存器结果状态表，指向本保留站

**此阶段实现了寄存器重命名**：真正的寄存器被替换为保留站号！

#### ② Execute（执行）

当保留站中两个操作数都就绪（Qj=Qk=0）：
- 启动执行
- 不断监听 CDB，若有匹配的结果广播，立即更新操作数值

#### ③ Write Result（写结果，WB）

执行完成后，将结果**广播到 CDB**：
- **所有**等待该保留站结果的保留站同时收到数据
- **寄存器文件**中对应的寄存器也同时更新
- 释放本保留站

### 6.6 CDB vs 普通数据总线

| 类型 | 数据流向 | 特点 |
|------|----------|------|
| 普通数据总线 | 数据 + **目标地址**（"送到哪里"）| 点对点 |
| **CDB（公共数据总线）** | 数据 + **来源标识**（"来自哪里"）| **广播**给所有等待者 |

CDB 格式：64位数据 + 4位功能部件源地址

等待某保留站结果的所有单元**同时收到广播** → 实现真正的并行数据转发。

### 6.7 Tomasulo 解决 WAR/WAW 冒险的原理

**WAR 冒险消除**：
- 指令发射时立即将寄存器值（或产生它的RS号）**复制到保留站**
- 即使后续指令覆盖了该寄存器，保留站里已经有旧值 → WAR 冒险消失

**WAW 冒险消除**：
- 寄存器结果状态表只指向**最后一条**写该寄存器的指令
- 先前写同一寄存器的指令不影响后续读 → WAW 冒险消失

### 6.8 Tomasulo 的三大优势

1. **分布式冒险检测逻辑**：通过保留站和 CDB 实现，多条等待同一结果的指令可以**同时被释放执行**
2. **消除 WAW 和 WAR 停顿**：寄存器重命名彻底解决名称依赖
3. **跨基本块调度**：整数部件可以越过分支继续发射，使 FP 操作能跨越基本块

### 6.9 Tomasulo 的缺点

- **硬件复杂**：CDB 需要高速连接所有功能部件，电容大、布线密
- **CDB 成为瓶颈**：每个时钟周期只能有一个结果广播（多个 CDB 可改善但更复杂）
- **非精确中断（Imprecise Interrupts）**：乱序完成导致中断时无法精确确定是哪条指令出错 → 需要 ROB（重排序缓冲区）解决

## 七、显式寄存器重命名（Explicit Register Renaming）

### 7.1 原理

**思路**：维护一个**比 ISA 寄存器更大的物理寄存器文件**，每次指令写寄存器时，从**空闲列表（Free List）**中分配一个新的物理寄存器。

- 类似编译器的 **SSA（静态单赋值）形式**，但在硬件中动态完成
- **重命名表（Rename Table / Map Table）**：ISA 寄存器 → 物理寄存器的映射
- 每次写 ISA 寄存器时，更新重命名表，老物理寄存器最终释放回空闲列表

**效果**：彻底消除 WAR 和 WAW 冒险（每条写指令都有独立的物理目标寄存器）。

### 7.2 R10000 风格的显式重命名

```
ISA 寄存器: F0, F2, F4, ...
物理寄存器: P0, P2, P4, P32, P34, P36, ...

当前映射表（Current Map Table）：
  F0 → P32（最新写 F0 的物理寄存器）
  F4 → P4
  ...

空闲列表（Free List）：P60, P62, ...（可供分配的空闲物理寄存器）
```

**执行流程示例**：
```
LD   F0, 10(R2)  → 分配 P32，Map Table: F0→P32
ADDD F10,F4,F0   → 分配 P34，引用 P4(F4) 和 P32(F0)
DIVD F10,F34,F6  → 分配 P36，引用 P34(F10) 和 P6(F6)
BNE  P36, <...>  → 在此创建 Checkpoint（保存当前 Map Table）
```

**投机（Speculation）恢复**：若分支预测错误，只需**恢复到 Checkpoint 时的 Map Table**，并将分配的物理寄存器归还 Free List → 精确处理分支错误预测。

### 7.3 显式重命名与调度解耦

显式重命名的优势：
- 可以与任何调度方式组合（Scoreboard、Tomasulo 保留站等）
- 结果可以直接从物理寄存器文件读取（不需要从保留站或 ROB 中绕道）
- 有助于流水线平衡

**带显式重命名的 Scoreboard**：
- Issue 阶段：解码 + 检查结构冒险 + **分配新物理寄存器**
- Read Operands：等待无 RAW 冒险
- Execute：执行
- Write Back：写物理寄存器（无需检查 WAR/WAW！）

### 7.4 显式重命名的关键问题

1. **如何管理空闲列表（Free List）**：
   - 当一条指令提交（Commit）时，其目标物理寄存器的**旧版本**（被取代的那个）变为空闲
   - 需要按程序顺序提交，才能正确释放

2. **如何支持精确中断**：
   - 发生中断时，恢复到中断指令之前的 Map Table 状态（使用 Checkpoint 或按序提交）

## 八、Scoreboard vs Tomasulo 对比

| 特性 | Scoreboard（CDC6600）| Tomasulo（IBM 360/91）|
|------|---------------------|---------------------|
| 控制方式 | **集中式**（Scoreboard 全权负责）| **分布式**（保留站 + CDB）|
| WAW 冒险 | **停顿处理** | **寄存器重命名消除** |
| WAR 冒险 | **停顿处理** | **操作数复制到RS消除** |
| RAW 冒险 | 等待操作数就绪 | 等待操作数就绪 |
| 数据转发 | 从寄存器文件读 | CDB **广播** |
| 跨基本块 | 不支持 | 支持（整数部件可越过分支）|
| 结构 | 较简单 | 较复杂 |
| 中断处理 | 较好 | **非精确中断（需ROB）** |

## 九、总结

### 动态调度的核心贡献

```
动态调度
├── Scoreboard（CDC 6600, 1964）
│   ├── 乱序执行的第一个硬件实现
│   └── 局限：WAR/WAW 用停顿处理，集中控制
│
├── Tomasulo（IBM 360/91, 1966）
│   ├── 保留站：分布式等待队列
│   ├── 寄存器重命名：消除 WAR/WAW
│   ├── CDB：广播结果，支持多路等待
│   └── 局限：非精确中断，CDB 成瓶颈
│
└── 显式寄存器重命名（R10000 style）
    ├── 物理寄存器文件 > ISA 寄存器
    ├── 重命名表 + 空闲列表
    └── 与调度方式解耦
```

### 设计演进逻辑

1. 静态调度（编译器）：无运行时信息，难以处理内存依赖
2. 动态调度（硬件）：运行时检测依赖，乱序执行
3. 寄存器重命名：消除名称依赖，让更多指令可以并行

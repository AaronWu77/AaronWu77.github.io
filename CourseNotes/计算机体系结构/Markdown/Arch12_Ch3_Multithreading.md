## 一、为什么需要多线程？

### 1.1 超标量处理器的效率瓶颈

即使有乱序执行 + 多发射，超标量处理器的实际利用率也很低，主要因为：

| 原因 | 影响 |
|------|------|
| **Cache 缺失（Cache Miss）** | 内存访问需要数十到数百个周期，流水线大量空泡 |
| **分支预测错误** | 清空流水线，损失 10~20 个周期 |
| **数据依赖** | 后续指令必须等待前序指令结果 |

**单线程处理器** 在上述情况下无法填充流水线空泡 → 大量执行时间被浪费。

### 1.2 基本思想

**多线程（Multithreading）**：让处理器同时维护多个线程的执行上下文（PC、寄存器等），当一个线程因长延迟操作停顿时，**切换到另一个线程执行** → 用计算填充延迟，提高吞吐量。

**关键洞察**：硬件线程切换不需要操作系统干预（不同于进程切换），可以在单个时钟周期内完成。

## 二、软件多线程 vs. 硬件多线程

### 2.1 软件概念回顾

**进程（Process）**：
- 有独立的地址空间
- 可以包含多个线程

**线程（Thread）**：
- 独立的执行上下文：自己的 PC + 寄存器 + 栈
- 同一进程内的线程共享地址空间
- 通过多线程增加并发度、减少阻塞

### 2.2 硬件多线程（Hardware Multithreading）

**定义**：处理器能够执行多个软件线程。

**特点**：
- 线程可以"同时"执行（在硬件层面）
- 线程切换由**硬件控制**（无需 OS 干预）
- 线程之间**共享执行资源**（功能单元、Cache 等）→ 提高资源利用率，提高吞吐量
- 可以属于同一进程，也可以属于不同进程

## 三、多线程分类 ★

### 3.1 粗粒度多线程（Coarse-Grain Multithreading）

**原理**：
- 正常执行当前线程
- 只有当发生**长延迟事件**（如 L2/L3 Cache 缺失，需要数十周期）时，才切换到另一个线程
- 切换有一定代价（需要几个周期清空流水线）

**特点**：
- 对单线程性能影响**较小**（正常执行时不切换）
- 不能填充短延迟空泡（如 L1 Cache 缺失）
- 代表：IBM Power RS64-IV

### 3.2 细粒度多线程（Fine-Grain Multithreading）

**原理**：
- 每个时钟周期都轮转（Round-Robin）切换线程
- 即使某线程没有停顿，也会让给其他线程

**特点**：
- 可以隐藏所有延迟（包括短延迟）
- 单线程性能**下降**（因为每个线程都被频繁打断）
- 代表：Tera MTA（Multi-Threaded Architecture）

**Tera MTA**：
- 支持数百个线程的同时切换
- 目标：始终让处理器保持忙碌
- 每个周期从不同线程取指

### 3.3 垂直多线程（Vertical Multithreading）

与水平（同时）多线程相对的概念：
- 一个时刻只有一个线程在执行
- 遇到停顿时切换到下一个线程
- 类似粗粒度多线程的时间共享

### 3.4 同时多线程（Simultaneous Multithreading, SMT）★★

**原理**：
- 在**同一个时钟周期内**，从**多个不同线程**发射指令
- 充分利用超标量处理器的宽发射能力和乱序执行窗口
- 不同线程的指令可以同时填充不同的功能单元

**与动态超标量结合**：
- 乱序超标量处理器本来就在单个线程内寻找可并行的指令
- SMT 在此基础上：当单个线程的指令不足以填充所有功能单元时，从其他线程取指令来填充

**优势**：
- 不同线程的指令通常相互独立 → 天然没有数据依赖
- 即使单线程无法填满流水线，多线程组合也可以达到接近 100% 的功能单元利用率

## 四、SMT 设计挑战

### 4.1 细粒度 vs. 单线程性能的权衡

- **倾向于特定线程（Preferred Thread）**：某一个线程优先发射 → 可能牺牲其他线程的吞吐量
- 最大化单线程性能需要：尽量超前取指（Prefetch），分支预测错误时快速恢复

### 4.2 更大的寄存器文件

- 需要同时保存**多个线程的寄存器上下文**
- 寄存器文件面积增大，但不应影响关键路径（如发射、完成）

### 4.3 Cache 和 TLB 冲突

- 多个线程共享 Cache → 可能互相驱逐对方的数据（Cache 抖动）
- TLB（Translation Lookaside Buffer）需要用**线程 ID（Thread ID）** 标记条目，避免线程间混淆

## 五、Intel Pentium 4 超线程技术（HyperThreading, HT）★

### 5.1 HT 概念

Intel 将 SMT 商业化为 **Hyper-Threading（超线程）技术**：
- 对外表现为 2 个**逻辑处理器（Logical Processor）**
- 共享同一个物理处理器核心的大部分资源

### 5.2 前端（Front End）

**前端负责向后端发射指令（微操作）**：

**关键组件**：
- **Execution Trace Cache（执行踪迹缓存）**：缓存已解码的微操作序列（而非原始 80x86 指令）
- **Microcode Store ROM（MSROM）**：处理复杂 80x86 指令
- **ITLB（指令 TLB）+ 分支预测**：分支目标缓冲和分支预测器
- **IA-32 指令译码**：将 80x86 指令翻译为微操作
- **微操作队列（Micro-op Queue）**

**HT 下的前端工作**：
- **Trace Cache 命中**：两个逻辑处理器**每个时钟轮流**访问 TC
- **Trace Cache 缺失**：两个处理器**乒乓（Ping-Pong）** 访问 L2 Cache 进行填充；若一个处理器停顿，另一个可使用 TC 的全带宽

### 5.3 后端（Back End）

**分配器（Allocator）**：
- 分配 ROB 条目（共 126 项）：HT 开启时，每个逻辑处理器最多 **63 项**
- 分配物理寄存器（128 整数/FP 物理寄存器）：每个逻辑处理器各用一半
- 分配 Load/Store 缓冲（48 Load + 24 Store）：HT 时每处理器 24 Load + 12 Store

**寄存器重命名**：
- 两个逻辑处理器各有独立的 **RAT（Register Alias Table）**
- 重命名与分配器并行进行
- 微操作分别进入 MIAQ（内存指令地址队列）和 GIAQ（通用指令地址队列），两个逻辑处理器各占一半条目

**指令调度**：
- 5 个调度器，调度不同类型的微操作
- 基于操作数就绪和执行资源可用性调度
- 为防止死锁，每个逻辑处理器在调度器队列中有活跃条目数上限

**执行（Execution Units）**：
- 微操作执行完后放入 ROB（与调度器解耦）
- ROB 分区：每个逻辑处理器使用一半

**提交（Retirement）**：
- 追踪两个逻辑处理器哪些微操作可以提交
- **交替（Alternating）** 提交两个逻辑处理器的微操作

### 5.4 内存子系统

| 组件 | HT 特性 |
|------|---------|
| DTLB（数据 TLB）| 每个条目带**逻辑处理器 ID 标签**；预留寄存器保证公平性 |
| L1/L2/L3 Cache | **两个逻辑处理器共享所有层级的 Cache 条目**（无分区）|
| 总线（Bus）| 先来先服务，两个处理器平等；APIC 和中断资源独立 |

## 六、Sun T1（Niagara）处理器 ★

### 6.1 设计哲学：芯片多线程（CMT, Chip MultiThreading）

**单线程高性能设计的困境**：
- L2 Cache 越来越大，但性能提升越来越少（边际效益递减）
- 功耗效率下降
- 出现热点（Hot Spot）
- 处理器实际利用率低

**T1 的方向**：用多个**简单、低功耗的核心** + 大量线程，而非一个复杂超标量核心，面向**商业服务器工作负载**（高并发、多线程）。

### 6.2 T1 架构概览

| 参数 | 数值 |
|------|------|
| 核心数/芯片 | **8 核** |
| 线程数/核心 | **4 线程** |
| 总线程数 | **32 个硬件线程** |
| FPU | **8 核共享 1 个 FPU** |
| 核心互连 | 134.4 GB/s 交叉开关（Crossbar Switch）|
| L2 Cache | 12 路组相联，3MB，4 个 Bank |
| 内存通道 | 4 个 DDR2（峰值 23 GB/s）|
| 功耗 | < 80W |
| 晶体管数 | ~3 亿 |
| 芯片面积 | 378 mm² |

### 6.3 每个核心结构

**资源独占（每线程独立）**：
- 寄存器文件（窗口寄存器：8 全局 + 24 窗口寄存器，SPARC 架构风格）
- 指令取指数据通路的部分
- Store 缓冲 + Miss 缓冲（每线程 8 项 Store 缓冲，合并为 32 项统一数组）

**资源共享（4 线程共享）**：
- L1 I-Cache（16KB，4路，32B行）
- L1 D-Cache（8KB，4路，16B行）
- TLB（64项，全相联，支持 8K/64K/4M/256M 页面）
- 执行单元（ALU、移位器、乘除法器）
- 流水线寄存器和数据通路

**核心面积**：11 mm²（90nm），多线程增加约 20% 面积。

**流水线**：6 级，**单发射**（非超标量！）→ 硬件简单，功耗低。

### 6.4 线程选择策略（Thread Selection Policy）

T1 实现**细粒度多线程**：

- 每个时钟周期从**就绪线程**中选择一个执行
- 优先选择**最近最少执行的线程（Least-Recently-Executed）**
- 线程变为"非就绪"的原因：
  - **长延迟操作**：Load、分支、乘法、除法（Load/分支有 3 周期延迟）
  - **流水线停顿**：Cache 缺失、陷阱（Trap）、结构冒险

### 6.5 执行单元细节

- **单 ALU + 移位器**：复用于分支地址和虚拟地址计算
- **整数乘法器**：5 周期延迟，吞吐量 0.5/周期（每核同时只允许 1 个乘法）；乘法器与模运算单元（MAU）轮流共享
- **简单除法器**：每核同时只允许 1 个除法
- 若 MUL/DIV 单元已占用，发射该操作的线程**回滚并切换出去**

### 6.6 浮点单元（FPU）

T1 最特殊的设计：**8 核共享 1 个 FPU**（位于芯片中心，通过交叉开关连接）：

执行流程：
1. 核心检测到 FPop → 线程切换出去
2. FPop 进一步译码，读取 FRF（FP 寄存器文件）
3. FPop + 操作数打包，通过交叉开关发送到 FPU
4. FPU 执行，结果通过交叉开关返回
5. 写回 FRF，线程重新就绪

（设计假设：服务器工作负载几乎不用浮点 → 节省面积和功耗）

### 6.7 L2 Cache

- 3MB，4路 Bank，12路组相联，写回
- 64B Cache 行，64B 在 Bank 间交织
- 16个 Outstanding Miss / Bank，共 64 个
- **一致性协议**：用 L2 目录（Directory）存储 L1 标签的影子（Shadow）
  - 2048 目录条目（Icache/Dcache 各一半）
  - L1 缺失时：通过替换策略找到物理位置
  - Store 操作：写失效（Write Invalidate）
  - 向其他核心发送失效包（Invalidation Packet）

### 6.8 性能与功耗

**T1 vs. 传统 SMP（对称多处理器）**：

| 指标 | T1 表现 |
|------|---------|
| TPC-C（事务处理）| 高 |
| SPEC JBB 2005（Java 服务器）| 高 |
| Performance/Watt | **显著优于 ILP 密集型处理器** |

**结论**：
- 对于**多线程商业应用**（数据库、Web 服务器等），TLP（线程级并行）方法的功耗效率远高于 ILP 密集型方法
- CMT 为**在功耗约束下提高性能**提供了可行路径

## 七、不同多线程方案对比

| 方案 | 执行资源 | 线程粒度 | 单线程性能 | 吞吐量 |
|------|---------|---------|-----------|--------|
| 粗粒度多线程 | 共享（时分） | 长延迟时切换 | 较好 | 中等 |
| 细粒度多线程 | 共享（时分） | 每周期切换 | 较差 | 较好 |
| SMT（超线程） | 同时使用（空分） | 多线程同时发射 | 中等（约 +15~30%）| 很好 |
| 多核（CMP/CMT）| 每核独立 | 独立运行 | 好（单核性能）| 最好（整体）|

## 八、总结

```
多线程的价值：
  流水线空泡（Cache缺失、分支误预测、数据依赖）
       ↓
  多线程填充空泡
       ↓
  硬件利用率提升 → 整体吞吐量提升

三种粒度：
  粗粒度：长延迟时切换（代表：IBM Power RS64）
  细粒度：每周期切换（代表：Tera MTA）
  同时（SMT）：同周期多线程发射（代表：Intel HT / Sun T1 per-core）

CMT（芯片级多线程）代表了服务器领域的设计趋势：
  多核 × 多线程 × 共享资源
  → 高并发吞吐 + 优秀的性能/瓦特比
```

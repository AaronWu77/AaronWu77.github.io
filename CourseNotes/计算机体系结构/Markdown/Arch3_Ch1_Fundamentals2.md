## 一、成本趋势（Cost Trends）

### 1.1 影响成本的三大因素

| 因素 | 说明 |
|------|------|
| **时间（Time）** | 即使没有重大工艺改进，元器件价格也会随时间下降 |
| **批量（Volume）** | 产量越大，单件制造效率越高，成本越低 |
| **商品化（Commodification）** | 供应商竞争导致整体产品成本下降 |

### 1.2 集成电路的成本构成

**制造一颗芯片的成本**：

```
晶圆成本（Wafer Cost）
       ↓
芯片成本 = 晶圆成本 / 每片晶圆上的良品芯片数
```

$$\text{每片良品芯片数} = \frac{\text{每片晶圆的芯片数} \times \text{晶圆良率}}{\text{芯片良率}}$$

### 1.3 从成本到售价

| 层次 | 说明 |
|------|------|
| **零件成本（Component Cost）** | 原材料成本 |
| **直接成本（Direct Cost）** | 生产单件产品的直接费用，通常为零件成本的 +20%~40% |
| **毛利（Gross Margin / 间接成本）** | 研发、市场、税收等，通常收入的 4%~12% 用于研发 |
| **平均售价（ASP）** | 零件成本 + 直接成本 + 间接成本 |

**成本与价格的杠杆效应**：  
设计决策使成本增加 1000 美元 → 最终售价**增加 3000~4000 美元**！  
这是因为价格必须覆盖直接成本和间接成本的比例放大。  
因此，**降低成本的设计决策具有远超直觉的商业价值**。

## 二、可靠性（Dependability）

### 2.1 概念辨析

**可依赖性（Dependability）** 是一个广义术语，涵盖：
- 可靠性（Reliability）
- 安全性（Security）
- 可用性（Availability）

> **可靠性（Reliability）**：在指定使命周期内，系统持续提供正确服务的能力（关注"是否会故障"）  
> **可用性（Availability）**：系统在任意时刻可以正常运行的概率（关注"故障了多久"）

### 2.2 两大核心度量

#### 模块可靠性（Module Reliability）

| 指标 | 英文全称 | 含义 |
|------|----------|------|
| **MTTF** | Mean Time To Failure | 平均故障前工作时间 |
| **MTTR** | Mean Time To Repair | 平均修复时间 |
| **FIT** | Failure In Time | 故障率 = 1/MTTF（每十亿小时的故障次数） |
| **MTBF** | Mean Time Between Failure | 平均故障间隔时间 = MTTF + MTTR |

> **FIT（Failure In Time）**：通常以每十亿（10⁹）器件小时为单位，  
> 例如：FIT = 1000 表示每十亿器件小时发生 1000 次故障，即单个器件的 MTTF = 10⁶ 小时 ≈ 114 年。

#### 模块可用性（Module Availability）

对于有修复能力的非冗余系统：

$$\text{Module Availability} = \frac{MTTF}{MTTF + MTTR}$$

**例子**：若 MTTF = 1000 小时，MTTR = 1 小时，则：
$$\text{Availability} = \frac{1000}{1001} \approx 99.9\%$$

### 2.3 常见误区（Pitfall）

> **谬误**：磁盘的额定 MTTF 为 1,200,000 小时（约140年），所以磁盘几乎永远不会坏。

**实际情况**（Gray & van Ingen, 2005 调查）：  
真实环境中，磁盘每年故障率为 **3%~7%**，对应实际 MTTF 约 **125,000~300,000 小时**——远低于额定值！

原因：额定 MTTF 是在受控实验室条件下测量的，真实使用环境（温度、振动、使用模式）差异显著。

## 三、性能测量与报告

### 3.1 什么是性能？

性能的定义因对象不同而不同：

| 视角 | 关注点 | 度量方式 |
|------|--------|----------|
| **用户** | 程序跑多快 | 响应时间（Response Time / Latency） |
| **管理员** | 系统吞吐能力 | 吞吐量（Throughput） |
| **CPU设计师** | CPU本身有多快 | CPU时间（CPU Time） |

**性能的基本公式**：

$$\text{Performance} = \frac{1}{\text{Execution Time}}$$

$$\text{Speedup}(A/B) = \frac{\text{Performance}_A}{\text{Performance}_B} = \frac{\text{Execution Time}_B}{\text{Execution Time}_A}$$

### 3.2 响应时间（Response Time / Wall-Clock Time）

- **定义**：从程序开始到程序结束的总时钟时间
- 也称为 **Elapsed Time**（经过时间）
- 包括：CPU计算时间 + 内存访问 + I/O + OS开销 + 多道程序切换开销
- **反映用户的实际感受**

**局限性**：
- 多程序并发时，wall-clock time 包含其他进程的干扰
- 若程序等待用户输入，时间会虚高

### 3.3 CPU时间（CPU Time）

- **定义**：CPU实际执行该程序的时间，**不包括等待 I/O 的时间**
- 分为：
  - **用户 CPU 时间**：花在用户代码上的时间
  - **系统 CPU 时间**：花在系统调用（如 printf、malloc）上的时间
- **反映 CPU 设计者关心的性能**

Unix `time` 命令输出示例：
```
90.7u  12.9s  2:39  65%
```
- `90.7u`：用户 CPU 时间 90.7 秒
- `12.9s`：系统 CPU 时间 12.9 秒
- `2:39`：总 wall-clock 时间 2分39秒（= 159秒）
- `65%`：CPU 使用率 65%（(90.7+12.9)/159 ≈ 65%）

### 3.4 吞吐量（Throughput）

- **定义**：单位时间内完成的工作量
- 示例：每天代码行数、每秒传输比特数、每秒处理的网页请求数
- **服务器、数据中心最关注的指标**

**响应时间 vs 吞吐量的关系**：
- 提升响应时间 → 通常同时提升吞吐量（CPU更快）
- 提升吞吐量 → **不一定**提升响应时间（增加处理器数量，任务并行执行）

### 3.5 MIPS（Millions of Instructions Per Second）

$$\text{MIPS} = \frac{\text{Instruction Count}}{时间 \times 10^6}$$

**MIPS 的局限性**：
- 同一 ISA 的不同实现之间比较：**有一定参考价值**
- 不同 ISA 之间比较：**完全失去意义**！
  - 原因：不同 ISA 的指令"胖瘦"不同，同一任务在 ISA-A 上可能只需 10 条指令，在 ISA-B 上需要 100 条指令
  - MIPS 高的机器不一定跑得快

### 3.6 嵌入式系统的特殊指标

嵌入式系统的关键评估维度：
- 成本（Cost）
- 物理尺寸（Physical Size）
- 内存占用（Memory）
- **功耗（Power Consumption）和能效**

## 四、基准测试（Benchmarks）

### 4.1 基准测试的种类

| 类型 | 说明 | 可信度 |
|------|------|--------|
| **真实应用程序** | 实际使用的软件，最能反映真实性能 | ★★★★★ |
| **修改版应用程序** | 专注于特定特性 | ★★★★ |
| **核心程序（Kernels）** | 关键代码片段提取 | ★★★ |
| **合成基准（Synthetic）** | 人工构造，模拟平均指令混合（如 Dhrystone） | ★★ |
| **玩具程序（Toy）** | 极小程序，测量价值有限 | ★ |
| **数据库基准** | 独特的测试体系 | — |

**合成基准的问题**：  
编译器和硬件厂商可能针对这些基准进行**专门优化**，导致基准测试成绩虚高但真实应用没有对应提升。  
例如：$\sqrt{e^x} = e^{x/2}$，编译器可以识别 SQRT(EXP(x)) 并替换为 EXP(X/2)，合成基准测试收益大，真实程序未必有这个模式。

### 4.2 SPEC 基准测试套件

**SPEC（System Performance Evaluation Cooperative）** 成立于1988年，40+ 成员公司，是最广泛使用的处理器性能标准化测试组织。

**核心基准套件**：

| 版本 | 说明 |
|------|------|
| SPEC CPU 2017 | SPECspeed（时间指标）、SPECrate（吞吐量指标） |
| SPEC CPU 2017 INT | 12个整数密集型基准（来自真实应用） |
| SPEC CPU 2017 FP | 14个浮点密集型基准（来自科学计算） |
| SPECviewperf | OpenGL 图形基准 |

**运行基准的注意事项**：  
必须记录所有条件：程序输入、程序版本、编译器版本、优化级别、OS版本、内存大小、磁盘类型等。软件配置对基准结果有显著影响。

### 4.3 性能比较中的"均值陷阱"

**问题场景**：两台机器 A 和 B，跑两个程序，怎么比较？

|  | Program 1 | Program 2 |
|--|-----------|-----------|
| Machine A | 2 秒 | 12 秒 |
| Machine B | 4 秒 | 8 秒 |

三种算法给出三种答案：

**方法1：对 A 归一化的算术平均**
- 程序1：B/A = 4/2 = 2（A快2倍）
- 程序2：B/A = 8/12 = 0.67（A慢1.5倍）
- 平均 = (2 + 0.67)/2 = **1.33**（A快33%）

**方法2：对 B 归一化的算术平均**
- 程序1：A/B = 2/4 = 0.5
- 程序2：A/B = 12/8 = 1.5
- 平均 = (0.5 + 1.5)/2 = **1.0**（A和B一样快）

**方法3：总运行时间之比**
- A 总时间 = 2+12 = 14秒
- B 总时间 = 4+8 = 12秒
- A/B = 14/12 ≈ **1.17**（A慢17%）

**为什么会有三种不同答案？**
> 因为这三种方法回答的不是同一个问题！每个方法都是合理的，但适用场景不同。

### 4.4 三种均值的使用场景

#### 算术均值（Arithmetic Mean）

$$AM = \frac{1}{n}\sum_{i=1}^{n} t_i$$

- 适合：跟踪**总执行时间**
- 特点：执行时间长的程序权重更大（合理，因为长程序对用户影响更大）

#### 调和均值（Harmonic Mean）

$$HM = \frac{n}{\sum_{i=1}^{n}\frac{1}{r_i}}$$

- 适合：当性能以**速率**表示（如 MIPS、FLOPS）时的平均
- 调和均值才能跟踪总执行时间

#### 加权算术均值（Weighted Arithmetic Mean）

$$WM = \sum_{i=1}^{n} w_i \times t_i \quad \left(\sum w_i = 1\right)$$

- 考虑程序的**运行频率**（某些程序用户运行更多次）
- 更准确地反映真实工作负载下的性能

#### 几何均值（Geometric Mean）

$$GM = \left(\prod_{i=1}^{n} r_i\right)^{1/n}$$

- 适合：对**归一化后的速率比值**求平均
- 优点：**与参考机器无关**（不管选哪台机器做参考，几何均值的比值一致）
- 缺点：不能预测绝对运行时间，每个程序权重相同（忽略了程序长短差异）

**SPEC 官方使用几何均值**汇报性能，正是因为它的"与参考机器无关"特性。

**最终原则**：  
> 最理想的是：**测量真实工作负载，按使用频率加权**。其次，如果只能选一个：总执行时间/算术均值更诚实，几何均值更方便比较。

## 五、量化设计原理（Quantitative Principles）

这是**整个课程最重要的理论基础**，后续所有优化技术都基于这四条原理。

### 5.1 利用并行性（Take Advantage of Parallelism）

并行性是提高性能最重要的方法，可以在不同层次实现：

| 层次 | 技术 |
|------|------|
| **系统级** | 多处理器、集群 |
| **指令级（ILP）** | 流水线（Pipelining）|
| **操作级** | 组相联 Cache（多路并行查找）、流水线功能单元 |

每提高一个层次的并行性，都可以带来数量级的性能提升。

### 5.2 局部性原理（Principle of Locality）

这是 Cache 设计的理论基础！

> **程序趋向于反复使用它最近使用过的数据和指令。**

**经验法则**：程序 90% 的执行时间花在 10% 的代码上。

两种局部性：

| 类型 | 定义 | 举例 |
|------|------|------|
| **时间局部性（Temporal Locality）** | 最近访问的内容很可能在近期再次被访问 | 循环变量、热点函数 |
| **空间局部性（Spatial Locality）** | 地址相邻的内容倾向于被相近时间访问 | 数组遍历、顺序执行的指令 |

**应用**：
- Cache 的命中率高，根本原因就是程序具有强局部性
- 硬件预取（Prefetch）也基于空间局部性

### 5.3 聚焦常见情况（Focus on the Common Case）

> "简单是快的。频繁的情况往往更简单，可以做得更快。"

这条原理乍一听很直白，但蕴含深刻的工程智慧：

- **资源分配**：把更多的硬件/功耗预算分给最常被执行的路径
- **设计取舍**：为罕见情况增加复杂性不值得（高成本，低收益）
- Amdahl 定律是这一原理的量化形式

**例子**：
- 整数指令占 80%，浮点只占 20% → 优化整数 ALU 回报更高
- 分支预测准确率 95% → 优先优化预测正确的快速路径

### 5.4 Amdahl 定律（Amdahl's Law）

**这是体系结构设计中最重要的定量工具之一！**

#### 定律内容

> "使用某种更快执行模式所获得的性能提升，受限于该模式可被使用的时间比例。"

$$\text{Speedup}_{overall} = \frac{1}{(1 - F_{enhanced}) + \frac{F_{enhanced}}{S_{enhanced}}}$$

其中：
- $F_{enhanced}$：在**原始机器**上，能被加速的那部分的时间占比（注意：是原始机器的时间比例！）
- $S_{enhanced}$：加速部分的加速倍数

#### 关键推论

**上界定律**：若某部分只能被用于 $F$ 比例的时间，则无论对它优化多少倍，整体加速比**最大为**：

$$\text{Speedup}_{max} = \frac{1}{1 - F_{enhanced}}$$

例如：即使把 40% 占用时间的部分优化到无限快，整体加速比也不超过 $1/(1-0.4) = 1.67$。

#### 例题 1

**题目**：服务器 CPU 用于计算的时间占 40%，等待 I/O 时间占 60%。用 10 倍更快的 CPU 替换，总加速比是多少？

**解**：
$$\text{Speedup} = \frac{1}{0.6 + \frac{0.4}{10}} = \frac{1}{0.64} \approx 1.56$$

→ CPU 快了10倍，整体性能只提升了 56%！ 这说明 **I/O 是瓶颈**。

#### 例题 2（重要注意事项）

**题目**：某增强功能比原来快10倍，被使用 50% 的时间（以增强模式运行时的执行时间百分比计）。

⚠️ **陷阱**：题目说"增强模式使用50%的时间"，但 Amdahl 定律中的 $F$ 必须是**原始机器**上的时间比例，不是增强后的时间比例！

**正确做法**：设增强模式在原始机器上的时间比例为 $F$。如果增强后加速 10 倍，增强模式花 50% 的时间，则：

设原始总时间 = T，增强部分在原始机器时间 = $F \times T$，增强后时间 = $\frac{FT}{10}$。
非增强部分时间 = $(1-F)T$。
新总时间 = $(1-F)T + \frac{FT}{10}$。
增强模式占新总时间的 50%：
$$\frac{FT/10}{(1-F)T + FT/10} = 0.5$$
解得：$F = \frac{10}{11} \approx 0.909$（原始机器上 90.9% 的时间在增强模式）

$$\text{Speedup} = \frac{1}{1 - \frac{10}{11} + \frac{10/11}{10}} = \frac{1}{0.0909 + 0.0909} = \frac{1}{0.1818} \approx 5.5$$

#### Amdahl 定律的含义

1. **加速的上界**：无论多努力优化某一部分，整体提升受制于"未被优化的部分"
2. **资源分配指南**：告诉我们应该把精力放在**使用频率高**的部分
3. **避免局部最优**：不要在测量之前就大力优化某个功能（这是著名的 Pitfall）

### 5.5 CPU 性能方程（CPU Performance Equation / Iron Law）

这是计算 CPU 执行时间的**核心公式**：

$$\text{CPU Time} = \text{IC} \times \text{CPI} \times \text{Clock Cycle Time} = \frac{\text{IC} \times \text{CPI}}{\text{Clock Rate}}$$

三个因子：

| 因子 | 全称 | 影响者 |
|------|------|--------|
| **IC（Instruction Count）** | 指令数 | ISA 设计者、编译器 |
| **CPI（Cycles Per Instruction）** | 每条指令的平均时钟周期数 | 处理器设计者 |
| **Clock Cycle Time（1/时钟频率）** | 时钟周期时间 | 芯片设计者（工艺） |

**架构层次对应**：
```
ISA 设计 → 编译器设计 → 处理器设计 → 芯片设计
   IC          IC          CPI         时钟频率
```

**关键难点**：三个因子**互相耦合**，难以独立改变！
- 降低 CPI（增加流水线）→ 可能增加时钟周期时间
- 使用更复杂指令（降低 IC）→ 可能增加 CPI
- 提高时钟频率 → 可能需要更简单的电路，影响 CPI

#### 综合 CPI 计算

$$\text{CPU Time} = \sum_{i=1}^{n} IC_i \times CPI_i \times \text{Clock Cycle Time}$$

$$\text{Average CPI} = \sum_{i=1}^{n} \frac{IC_i}{IC_{total}} \times CPI_i$$

#### 例题：两种设计方案比较

**题目**：
- 浮点运算（不含FPSQR）频率 25%，平均 CPI = 4.0
- 其他指令频率 73%，平均 CPI = 1.33
- FPSQR（浮点开方）频率 2%，CPI = 20

**方案A**：将 FPSQR 的 CPI 降到 2  
**方案B**：将所有浮点运算的平均 CPI 降到 2.5

**解**：

基础 CPI = 0.25×4.0 + 0.73×1.33 + 0.02×20 = 1.0 + 0.97 + 0.4 = **2.37**

**方案A**：CPI = 0.25×4.0 + 0.73×1.33 + 0.02×2 = 1.0 + 0.97 + 0.04 = **2.01**

**方案B**：CPI = 0.25×2.5 + 0.73×1.33 + 0.02×2.5 = 0.625 + 0.97 + 0.05 = **1.645**

→ **方案B 更优**（CPI 更低），因为它优化了所有浮点运算（占25%），而方案A只优化了 FPSQR（仅2%）。  
→ 这与 Amdahl 定律一致：**提升更大比例的部分，获益更多**。

## 七、常见谬误与陷阱（Fallacies & Pitfalls）

### 谬误（Fallacy）

1. **"基准测试永久有效"**  
   → 错！应用特征随时间变化，某些曾经重要的基准已不能反映现代工作负载。

2. **"磁盘额定 MTTF 140年，所以磁盘几乎不会坏"**  
   → 错！实际每年故障率 3%~7%，与额定差距达数倍。额定值是理想实验室环境测量的。

3. **"峰值性能 = 实际性能"**  
   → 错！峰值性能（Peak Performance）通常无法在真实应用中达到，不能用于预测实际性能。

4. **"处理器成本主导系统成本"**  
   → 错！内存、存储、电源、散热、主板等综合起来可能超过处理器本身。

### 陷阱（Pitfall）

1. **在测量使用频率之前就大力优化某功能**  
   → Amdahl 定律的陷阱：如果该功能实际上只占 2% 的执行时间（如 FPSQR），无论优化多少倍都没有意义。

2. **单点故障（Single Point of Failure）**  
   → 即使把电源做得无比可靠，如果散热风扇是单点故障，系统可靠性仍受风扇限制。

3. **故障检测反而降低可用性**  
   → 有些硬件状态（如分支预测器的状态）对程序正确性不是必须的。激进地检测故障却不修复，会降低可用性。

## 八、总结

本章建立了**量化体系结构**的完整分析框架：

| 原理 | 应用 |
|------|------|
| **并行性** | 流水线、多核、向量 |
| **局部性** | Cache 层次结构 |
| **聚焦常见情况** | 资源分配、分支预测优化 |
| **Amdahl 定律** | 量化优化收益，避免无效优化 |
| **CPU 性能方程** | IC × CPI × 时钟周期时间 |

**最重要的认知**：

1. **"快了一部分"不等于"快了整体"** —— Amdahl 定律的核心教训
2. **性能比较必须严谨**——算术均值/几何均值选择不当会得出完全相反的结论
3. **基准测试 ≠ 真实性能**——最终答案是"你的应用跑多快"
4. **CPU 性能方程的三个因子相互制约**——优化不能只看一个维度
